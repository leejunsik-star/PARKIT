# 29. 파인튜닝 모델(M1~M8)과 자체 모델(mymodel) 성능 비교 (2026-11-01)

대상: `docs\도구\models\` 의 모델 11개
- **M1~M8**: YOLO26n 사전학습 모델을 우리 데이터로 추가 학습(hun, 18·21 문서)
- **mymodel_M1 / M5 / M8**: 동료가 처음부터 만든 PARKIT Tiny 모델(`model.py`), 사전학습 없음

시험 사진: `dataset\split_3차`의 T1~T8 (21 문서와 같은 묶음)
채점 스크립트: `docs\도구\eval_모델비교.py` (클라우드 CPU에서 실행)

## 1. 결론

- **M8이 여전히 가장 좋다.** 차 있는 사진 510대 중 놓친 차 3대, 잘못 잡은 상자 12개, 차 없는 사진 오탐 3개.
- **자체 모델 중에서는 mymodel_M8이 가장 낫다.** 놓친 차는 14대로 M5와 같은 수준까지 왔다. 특히 T6(차+물체)에서 놓친 차가 0대다.
- **자체 모델의 가장 큰 약점은 잘못 잡은 상자다.** mymodel_M8은 차 있는 사진에서 171개(M8의 약 14배), 차 없는 사진에서 55개다. 절반 이상은 **차 한 대 안에 작은 상자가 하나 더 생기는 것**이고(4절), 진짜 배경·물체 오탐은 약 50개다.
- **자체 모델도 데이터가 늘수록 확실히 좋아졌다.** mymodel_M1 → M5 → M8로 놓친 차 97 → 46 → 14대, 차 없는 사진 오탐 1,841 → 48 → 55개.
- **같은 데이터라도 사전학습 차이가 크다.** M1과 mymodel_M1은 둘 다 1차 데이터만 썼다고 보면(아래 6절 확인 필요), 학교 사진 T2의 mAP50이 0.977 대 0.700이다.
- **속도·크기는 자체 모델이 작지만 빠르지는 않다.** 파라미터는 약 1/4(0.60M 대 2.53M), 연산량도 4.0 대 6.0 GFLOPs로 적지만, CPU 프레임당 시간은 오히려 조금 느렸다(57ms 대 46ms, 3절).

## 2. 구조 확인과 live_detect_winmac.py

- mymodel_M1, M5, M8 세 파일 모두 **같은 구조**다. 가중치 이름 124개와 모양이 모두 같고, 폭(width) 16, 입력 640이다. 지금 `docs\도구\model.py`로 세 파일 모두 오류 없이 불러진다.
- mymodel_M8에는 학습 정보(`dataset_recipe: M8`, 100 epoch 완료, 87 epoch 가중치 저장 등)가 더 들어 있지만, 불러오는 데는 영향이 없다.
- `live_detect_winmac.py`(2026-11-01 13:38 PC 파일)의 `Detector`로 세 모델을 실제로 불러 봤고 모두 `ParkitTiny`로 정상 인식됐다. **코드 수정은 필요 없다.** 이 문서의 채점도 이 코드의 `Detector.run()`을 그대로 써서, 실시간 프로그램과 같은 전처리로 잰 숫자다.

## 3. 채점 방법

- 놓친 차·잘못 잡은 상자: 신뢰도 0.25 이상 상자를, 신뢰도 높은 것부터 정답과 IoU 0.5 이상으로 1:1 짝지어 셈(21 문서와 같은 방식).
- mAP50: 신뢰도 0.001 이상 상자로 직접 계산(IoU 0.5, 101점 보간). 두 종류 모델에 같은 계산을 쓰려고 ultralytics `model.val` 대신 직접 셌다.
- **확인:** M5~M8의 놓친 차·잘못 잡은 상자 수는 21 문서(eval_3차.md)와 모두 같게 나왔다.
- 속도: 클라우드 CPU 4스레드, T2 사진 10장의 중간값, 신뢰도 0.25. YOLO는 640×384로(비율 유지), 자체 모델은 640×640으로(정사각형 패딩) 들어가서 실제 계산량 차이가 줄어든다.

## 5. 자체 모델이 잘못 잡는 상자의 종류

신뢰도 0.25에서 차 있는 사진(T1·T2·T3·T6·T8)의 잘못 잡은 상자를 나눠 봤다.

| 모델 | 같은 차에 겹친 상자 (IoU 0.5 이상) | 차 안쪽 일부만 잡은 상자 | 배경·물체 | 합계 |
|---|---|---|---|---|
| mymodel_M5 | 22 | 54 | 46 | 122 |
| mymodel_M8 | 24 | 99 | 48 | 171 |

- **잘못 잡은 상자의 72%(171개 중 123개)가 실제 차 위에 있다.** 차 한 대에 큰 상자와 작은 상자(차 앞부분이나 뒷부분만)가 같이 나오는 형태다. 칸 점유 판정에서는 차가 있는 칸을 비었다고 하지는 않지만, 접지점이 두 개 생겨 옆 칸까지 찬 것으로 볼 수 있다.
- 이 종류는 지금 다른 스레드에서 `live_detect_winmac.py`에 넣고 있는 **"큰 상자 안에 들어간 작은 상자 지우기" 옵션**으로 상당 부분 줄어들 것으로 본다(추정). 그 옵션이 들어오면 이 문서의 채점을 한 번 더 돌려 확인할 수 있다.
- 기준을 IoU 0.3으로 낮춰도 mymodel_M8의 놓친 차가 14 → 9대, 잘못 잡은 상자가 171 → 166개라, 상자 위치가 조금 어긋나서 틀린 것은 많지 않다.

## 6. 주의할 점

1. **동료 모델의 학습 데이터가 우리 M1/M5/M8과 정확히 같은지 확인하지 않았다.** 이름과 mymodel_M8 파일 안의 `dataset_recipe: M8` 기록으로 같은 조합이라고 보고 비교했다. 특히 **동료가 split_3차의 test 사진을 학습이나 모델 고르기에 쓰지 않았는지** 확인이 필요하다. 썼다면 자체 모델 점수는 실제보다 좋게 나온 것이다.
2. mymodel_M1 파일은 `docs\도구\mymodel.pt`(10-26)와 크기·날짜가 같아, 처음 받은 모델과 같은 것으로 보인다.
3. 21 문서 5절의 주의점이 그대로 적용된다. T6·T7은 학습 물체와 겹칠 수 있고, T7(6장)·T8(4장)은 사진이 적다. T8은 모든 모델이 거의 만점이라 구별이 안 된다.
4. 속도는 클라우드 CPU 기준이다. 시연 노트북에서는 다를 수 있으니 실시간 프로그램 화면의 프레임 시간으로 한 번 더 본다.
