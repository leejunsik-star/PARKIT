### 3.6 현재 연동 방식의 문제점 (2학기 확장과 직접 관련)

1. **앱이 `zones` 배열 전체를 덮어씁니다.** 칸 하나를 바꿔도 해당 주차장의 모든 층 데이터를 다시 씁니다 (`ParkingDetailActivity.java:421, 440, 465`). 엣지가 자주 상태를 쓰기 시작하면 트랜잭션 충돌과 쓰기 비용이 커집니다.
2. **앱이 다시 쓸 때 모르는 필드를 지웁니다.** `getZonesMapList()`(`ParkingSpot.java:139-184`)는 앱이 아는 필드만 직렬화하므로, 사용자가 한 번 주차 등록을 하면 `bg_img_with_spots`, `created_at`과 앞으로 추가할 `status` 같은 새 필드가 모두 사라집니다. 관리자 웹은 `created_at`으로 층 순서를 정렬하므로(`App.js:686`) 순서도 영향을 받습니다 (추론).
3. **앱은 `parking_lots.current`를 갱신하지 않습니다.** 주차 등록/취소 트랜잭션은 `zones`만 바꾸므로, 관리자 웹에서 다시 저장하기 전까지 지도 마커와 즐겨찾기 카드의 잔여 면수가 실제 칸 상태와 어긋납니다.
4. **점유 상태의 출처가 둘입니다.** 1학기에는 사용자가 직접 "주차 등록"을 해서 `occupied`를 true로 만들었고, 관리자 웹도 브러시로 점유를 바꿉니다(`App.js:1307, 3015`). 2학기에는 엣지(YOLO)가 점유를 판정하므로, 사용자의 "내 차 위치 기록"과 칸 점유 상태를 분리해야 합니다.

## 4. Canvas 렌더링 (`ParkingMapView`)

### 4.1 그리는 순서

1. **데이터 주입**: `setZoneData(zone, parkingId)` (`ParkingMapView.java:144-157`)가 줌/팬을 초기화하고 `bg_img_empty` 이미지를 백그라운드 스레드에서 내려받아 static `HashMap`에 캐시합니다 (`:162-186`).
2. **최초 1회 화면 맞춤**: 배경 크기(`bitmap 크기 × bg_scale`)를 뷰에 90%로 맞추고 중앙 정렬 (`:193-209`).
3. **캔버스 변환**: `translate(posX, posY)` → `scale(scaleFactor)` (`:213-215`). 이후 모든 좌표는 "도면 좌표계"에서 그립니다.
4. **배경 이미지**: `(bg_pos_x, bg_pos_y)`에서 `bitmap.width × bg_scale_x`, `bitmap.height × bg_scale_y` 크기로 그림 (`:218-222`).
5. **주차칸**: 칸마다 그룹을 찾아 회전 행렬로 중심 좌표를 구하고, `translate + rotate` 후 둥근 사각형을 그림 (`:225-360`).
   - 중심: `cx = localX + w/2`, `cy = localY + h/2`, `globalX = group.x + (cx·cos − cy·sin)`, `globalY = group.y + (cx·sin + cy·cos)` (`:264-273`)
   - 칸 크기는 Firestore에 저장되지 않고 타입별 상수입니다 (`getSpotSpec`, `:379-420`). NORMAL/EV/PATRIOT/WOMAN 40×80, COMPACT 35×70, HANDICAP 55×80. 관리자 웹의 `SPOT_TYPES`와 값이 같아야 합니다.
6. **터치 처리**: 단일 탭 좌표를 줌/팬 역변환하고, 그룹 회전을 역적용한 뒤 사각형 포함 여부로 칸을 찾음 (`:106-139`). 더블탭은 줌 초기화, 핀치 줌 범위는 최소(화면 맞춤 × 0.5) ~ 최대 5배 (`:490-520`).

### 4.2 좌표 단위

- **픽셀 계열의 "도면 좌표"입니다. 비율(0~1)도 미터도 아닙니다.**
  - `groups[].x/y`, `spots[].localX/localY`, `bg_pos_x/y`, 칸 크기(40×80 등)가 모두 같은 좌표계를 씁니다. 이 좌표계는 관리자 웹 Konva 스테이지의 픽셀 좌표와 같습니다 (`firestore_schema.md` 4장, 관리자 웹 `SPOT_TYPES`).
  - 배경 이미지는 원본 픽셀 크기에 `bg_scale`을 곱해서 이 좌표계에 맞춥니다. 따라서 도면 좌표 1단위가 실제 몇 미터인지 나타내는 값은 DB 어디에도 없습니다.
  - 화면에 그릴 때는 이 좌표에 `scaleFactor`만 곱하므로 dp 변환과 무관합니다. 테두리 두께와 모서리 반경만 `dp()`로 변환합니다 (`:427-429`).
- 2학기 호모그래피 결과(미터)를 도면에 올리려면 zone별로 "도면 좌표 ↔ 미터" 변환 정보(예: 원점, 1m당 도면 단위, 회전)가 새로 필요합니다. 어떤 형태로 둘지는 02 문서(스키마 설계)에서 정합니다.

### 4.3 상태별 색상 결정 코드

## 5. 위치 알림(Geofencing)과 경로 안내

### 5.1 도착 감지 ("지오펜싱")

- **Android Geofencing API(`GeofencingClient`)는 쓰지 않습니다.** 포그라운드 서비스에서 위치를 계속 받아 직접 거리를 계산하는 방식입니다.
- 구현: `LocationService.java`
  - 시작: `NaviHelper.startNavigation()`이 `dest_lat`, `dest_lng`, `parking_id`, `parking_name`을 넣어 `startForegroundService` 호출 (`NaviHelper.java:30-41`)
  - 위치 요청: `PRIORITY_HIGH_ACCURACY`, 4초 간격, 최소 2초 (`LocationService.java:84-124`)
  - 판정: `Location.distanceBetween`으로 목적지까지 거리 계산, **100m 이하**이면 도착 (`:93-111`). `NaviHelper` 주석에는 50m라고 되어 있어 코드와 다릅니다 (`NaviHelper.java:13`).
  - 도착 시: 위치 수신 중단 → 높은 우선순위 알림 + full-screen intent → `ParkingDetailActivity` 직접 실행 시도 → 서비스 종료 (`:126-159`)
  - 진행 중: 상시 알림에 "목적지까지 약 N m 남음" 갱신, "안내 중단" 액션으로 종료 (`:161-187`)
- 권한: `ACCESS_FINE/COARSE_LOCATION`, `FOREGROUND_SERVICE(_LOCATION)`, `POST_NOTIFICATIONS`, `USE_FULL_SCREEN_INTENT`, `SYSTEM_ALERT_WINDOW` (`AndroidManifest.xml:5-12`). `ACCESS_BACKGROUND_LOCATION`은 없습니다.
- 주의할 동작
  - "다른 앱 위에 표시" 권한이 없으면 설정 화면으로 보내고 **길찾기 자체를 시작하지 않고 return** 합니다 (`NaviHelper.java:19-28`).
  - `POST_NOTIFICATIONS` 런타임 권한 요청 코드는 없습니다. Android 13 이상에서 알림이 안 보일 수 있습니다 (추론, **확인 필요**).
  - Android 14 이상의 full-screen intent 제한이나 백그라운드 Activity 실행 제한에서 실제로 화면이 뜨는지는 **확인 필요**.
- 메인 화면의 내 위치 표시는 별도로 `MainActivity.java:531-603`에서 10초 간격 위치 업데이트로 처리합니다.

### 5.2 경로 안내

- **앱 안에 경로 안내 기능은 없습니다.** 외부 앱에 맡깁니다.
  - `kakaomap://route?ep={lat},{lng}&by=CAR` 딥링크로 카카오맵 앱 실행 (`NaviHelper.java:44-48`)
  - 실행에 실패하면(예외 발생 시) 구글맵 웹 길찾기 URL로 대체 (`:49-54`)
- 주차장 **내부**에서 빈 칸이나 내 차까지 안내하는 기능은 없습니다. 2학기 확장 모드(탑뷰 지도와 차량 위치)에서 새로 만들어야 하는 부분입니다.
- 진입점: 상세 화면 [길찾기] (`ParkingDetailActivity.java:253-257`), 즐겨찾기 카드 [길찾기] (`FavoriteAdapter.java:124-126`)

## 7. 마이그레이션 방향 제안

원칙: **추가 → 양쪽 호환 → 전환 → 제거** 순서로 바꿔서, 어느 단계에서 멈춰도 기존 앱과 관리자 웹이 깨지지 않게 합니다. 2학기 앱은 `Parkit/first`에서만 수정하고 원본 `E:\ccapstione\first`는 백업으로 둡니다.

| 단계 | 할 일 | 이유와 확인 방법 |
| :--- | :--- | :--- |
| 0. 백업과 기준선 | Firestore 데이터 내보내기(콘솔 또는 `gcloud firestore export`, 또는 스크립트로 JSON 덤프). 현재 앱이 빌드되고 실행되는지 확인. 가능하면 `Parkit`을 git 저장소로 만들어 기준 커밋 생성 | 되돌릴 지점 확보. 빌드 가능 여부는 1.4의 **확인 필요** 항목 |
| 1. 스키마 확정 (문서) | 02 문서에서 4단계 상태 필드, 상태 저장 위치(zones 배열 안 또는 별도 문서), 집계 정의, 미터 변환 필드, Realtime DB 경로를 확정 | 이후 단계의 기준. 특히 "칸 상태를 `zones` 배열 밖으로 뺄지"가 핵심 결정 |
| 2. 앱 읽기 호환 | `ParkingSpot`에 상태 enum 추가. 새 상태 필드가 있으면 그것을, 없으면 `occupied`로 EMPTY/OCCUPIED를 추정. `getZonesMapList()`가 모르는 필드를 보존하도록 수정 | 데이터 변경 전에 앱이 새 형식과 옛 형식을 모두 읽게 만듦. 이 단계만으로는 화면 변화 없음 |
| 3. 앱의 칸 상태 쓰기 제거 | 주차 등록/취소를 `users/{uid}`의 "내 차 위치"만 쓰도록 축소. `parkingspace` 쓰기 제거 후 Firestore 규칙으로 클라이언트의 `parkingspace` 쓰기를 관리자(owner)로 제한 | 3.6의 1, 2, 4번 문제 해결. 엣지와 사용자 입력 충돌 방지 |
| 4. 데이터 이행 (dual-write) | 기존 문서에 새 상태 필드를 채움(`occupied: true` → OCCUPIED, false → EMPTY). 한동안 `occupied`도 같이 유지. BLIND 상태일 때 옛 `occupied`에 무엇을 넣을지 결정 (**확인 필요**, 제안: 빈 칸으로 안내되지 않도록 true) | 옛 버전 앱이 설치된 기기도 계속 동작 |
| 5. 관리자 웹 동시 수정 | 상태 브러시를 4단계로, `parking_lots` 집계를 새 정의로, 칸 생성 기본값을 EMPTY로. 가능하면 집계는 Cloud Functions로 이동 | 관리자 웹이 저장할 때 새 필드를 지우지 않게 함 (6.2) |
| 6. 실시간 반영 | 상세 화면에 `addSnapshotListener` 적용(칸 상태가 별도 문서라면 해당 문서만 구독). 메인 지도는 집계만 주기적으로 또는 리스너로 갱신 | 엣지 상태가 화면에 바로 보이게 함 (3.3) |
| 7. 렌더링 4단계 | `ParkingMapView` 색상 분기를 4상태 + 내 차 + 자격 미해당 조합으로 재정의하고 범례 추가. 자격 판정 중복 코드 정리 | 사용자에게 보이는 변화는 이 단계부터 |
| 8. 미터 좌표와 확장 모드 | zone에 미터 변환 정보 추가 → 변환 함수 작성 → 기존 칸 좌표는 유지하고 변환으로 맞춤 → Realtime DB의 이동 차량 위치를 아이콘으로 그리는 레이어 추가 | 기존 도면 데이터를 다시 그리지 않고 확장 모드를 붙임 |
| 9. 정리 | 모든 클라이언트가 새 필드를 쓰는 것을 확인한 뒤 `occupied` 제거, 미사용 의존성(`androidx.print`)과 `Test.java` 정리 | 마지막에만 파괴적 변경 |

### 결정이 필요한 항목 (02 문서에서 다룰 것)

1. 칸 상태를 `zones[].spots[]` 안에 둘지, `parkingspace/{id}/spot_status/{spotId}` 같은 별도 문서나 맵으로 분리할지
2. `parking_lots.current`가 무엇을 세는지 (EMPTY만, 또는 BLIND 포함 여부)와 누가 계산하는지 (관리자 웹, Cloud Functions)
3. STATIC_BLIND / DYNAMIC_BLIND 칸을 사용자가 "내 차 위치"로 선택할 수 있는지
4. 도면 좌표 ↔ 미터 변환 정보의 형태 (zone별 원점과 축척, 회전 포함 여부)
5. 이동 차량 위치의 Realtime Database 경로와, 이용자 본인 차량을 식별하는 방법
