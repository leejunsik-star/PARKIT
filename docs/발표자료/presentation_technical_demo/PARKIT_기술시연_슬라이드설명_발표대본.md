## 1페이지. PARKIT 차량 추적과 2D 지도

### 그림과 기술 설명

이번 발표는 11월 3일 추적·웹 확장과 11월 4일 이동 방향 회전을 다룬다. 새 탐지 모델 학습 발표가 아니다. 기존 10장 자료보다 기술과 수치 예시를 늘리고 11~12장에서 실제 시연으로 전환한다.

### 발표 대본

이번 작업은 기존 PARKIT 차량 탐지와 점유 판정 결과를 이용해 차량별 ID를 추적하고, 사용자용 2D 지도로 연결하는 확장입니다. 기존 점유 알고리즘은 유지하면서 좌표 변환, 차량 연결, 실시간 전송, 사용자 화면을 구성했습니다. 먼저 실제 코드의 데이터 흐름과 매칭 계산을 설명한 뒤, 차량 선택과 이동 방향 회전, Follow 모드를 시연하겠습니다.

### 화면 조작과 진행

표지에서는 브라우저를 아직 열지 않는다. 전체 설명 9~11분, 시연 2~3분을 기준으로 연습한다.

### 예상 질문

## 2페이지. 기존 분석 결과에서 분기하는 구조

### 그림과 기술 설명

occupancy.py의 Engine이 모델 추론과 judge_frame을 실행한다. 같은 FrameResult를 기존 주차면 Tracker와 신규 TrackingBridge/VehicleTracker가 각각 사용한다. 두 결과의 복사본을 StateStore에서 묶는다. 기존 주차면 Tracker는 차량 ID용으로 재사용하지 않았다.

### 발표 대본

입력은 카메라 영상이고, 기존 YOLO 또는 PARKIT Tiny가 차량을 탐지합니다. judge_frame에서 좌표와 주차면 관측을 구하면 결과가 두 경로로 나뉩니다. 기존 Tracker는 각 칸이 비었는지 관리하고, 신규 VehicleTracker는 개별 차량의 이동을 관리합니다. TrackingBridge는 기존 결과에서 차량 접점과 시각을 읽어 새 추적기의 입력으로 바꿉니다. 이렇게 분리한 이유는 관리 대상과 시간 조건이 다르기 때문입니다. 차량 추적을 추가하면서 기존 점유 판정 규칙을 함께 바꾸지 않도록 했습니다.

### 화면 조작과 진행

도식의 공통 입력, 기존 초록 경로, 신규 파랑 경로 순서로 가리킨다.

### 예상 질문

Tracker가 둘인 이유는? → 기존은 고정 주차면의 상태, 신규는 이동 차량의 ID를 관리한다.

## 3페이지. Homography: 픽셀을 매트 cm로 변환

### 그림과 기술 설명

접점은 박스 아래 변 중앙이다. H는 이미지와 매트 기준점 대응으로 계산한 3×3 행렬이다. s는 동차 좌표의 배율이며 실제 x,y는 행렬 곱 결과를 세 번째 성분으로 나눠 구한다. 예시 픽셀과 cm 값은 계산 과정 설명용이며 실제 보정 실측값이 아니다.

### 발표 대본

카메라의 픽셀 위치는 촬영 방향과 원근에 영향을 받기 때문에 바로 거리로 비교할 수 없습니다. 먼저 탐지 박스의 아래쪽 중앙을 접점으로 잡고, 기존 보정 행렬 H를 적용해 매트의 센티미터 좌표로 바꿉니다. H는 보정 화면에서 지정한 영상 기준점과 실제 매트 좌표의 대응으로 계산합니다. 매트가 평평하고 카메라가 고정돼 있으므로 바닥 평면의 2D 변환이 현재 목적에 적합합니다. 최소 네 쌍의 정상 배치된 기준점이 필요하고, 실제 화면에서는 넓게 분산된 6~8점을 권장합니다. 카메라를 움직이면 다시 보정해야 하며, 이 접점은 실제 차체 중심의 근사값이라는 한계가 있습니다.

### 화면 조작과 진행

작은 식을 읽기보다 픽셀, H, cm 세 부분을 짚는다. 오른쪽 카메라로 옮겼을 때 재보정이 필요한 이유를 여기서 설명할 수 있다.

### 예상 질문

H는 학습된 가중치인가? → 신경망 학습 가중치가 아니라 수동 기준점 대응으로 계산한 기하 변환 행렬이다.

## 4페이지. 관측값과 차량 기록의 구분

### 그림과 기술 설명

Observation은 camera_id, observed_at, x,y, confidence, slot,kind,reliable을 담는다. 여기에 Global ID는 없다. Vehicle은 ID와 최근 위치·속도·카메라별 관측을 유지한다. 카메라 ID가 Global ID로 변환되는 것이 아니라 관측이 기존 차량 기록에 연결된다.

### 발표 대본

관측값은 어느 카메라가 언제 어디에서 차량을 봤는지를 담은 측정 자료입니다. 예를 들어 CAM-1이 0.4초에 22, 15센티미터 위치를 봤다는 기록입니다. 반면 차량 기록은 이전 관측을 연결해 유지하는 장부이며 Global ID와 속도, 마지막 관측 시각을 가지고 있습니다. 새 관측이 들어오면 이 장부의 어떤 차량에 붙일지 결정합니다. 따라서 CAM-1이라는 이름이 차량 번호로 바뀌는 것은 아닙니다. 하나의 Global ID 안에 CAM-1과 CAM-2의 관측이 함께 들어갈 수 있습니다. 잘린 상자나 매트 밖 접점, 오래되거나 중복된 프레임은 추적 갱신에서 제외합니다.

### 화면 조작과 진행

CAM-1과 G-0001은 서로 다른 종류의 ID라고 명확히 구분한다. G-0001은 슬라이드용 축약이며 실제 ID는 세션 접두어를 포함한다.

### 예상 질문

Local ID를 합치는가? → 현재 별도 카메라별 Local ID 없이 관측을 Global ID에 직접 연결한다.

## 5페이지. 매칭 전 이동 가능성 검사

### 그림과 기술 설명

_cost는 먼저 최근 원시 관측과 새 관측의 거리 delta가 vmax×dt+noise를 넘는지 검사한다. 그다음 예상 위치 오차를 비용으로 쓴다. 기본 gate=min(10cm,1cm+35cm/s×dt)이며 새 카메라는 1초 이내, gate 최대 2cm 조건이 추가된다. 이 슬라이드의 8cm는 첫 이동 가능성 검사 예시다.

### 발표 대본

가까운 관측이라고 무조건 같은 차로 연결하지 않습니다. 먼저 시간 차이와 최대 속도로 이동 가능한 범위를 검사합니다. 예를 들어 0.2초 간격이고 최대 속도 기본값이 초당 35센티미터, 오차 여유가 1센티미터라면 첫 검사에서 허용하는 이동량은 8센티미터입니다. 이를 넘는 후보는 제외합니다. 다음에는 최근 속도로 예측한 위치와 새 관측의 거리를 비용으로 계산합니다. 비용이 작을수록 연결 후보로 유리합니다. 최대 속도와 오차 여유는 실제 측정으로 조절할 초기 설정값입니다. 현재는 칼만 필터가 아니라 속도 예측과 지수 평활화를 사용합니다.

### 화면 조작과 진행

0.2×35+1=8을 설명하고 비용은 별도로 ‘예상 위치와의 거리’라는 점을 짚는다.

### 예상 질문

왜 게이트가 필요한가? → 최적화 알고리즘에 물리적으로 불가능한 연결을 맡기지 않기 위해 먼저 배제한다.

## 6페이지. Hungarian: 전체 비용의 일대일 할당

### 그림과 기술 설명

예시는 게이트를 통과한 비용표다. A부터 가장 가까운 탐지를 고르면 1+5.5=6.5, 교차 배정하면 3+2=5다. 현재 assign 함수로 이 예시의 최적 배정을 확인했다. 모호성 차이 0.65cm 이내 후보는 할당 전에 보류하며, 가상 미연결 열을 추가해 강제 매칭을 막는다.

### 발표 대본

차량이 여러 대면 각 차량이 순서대로 가까운 관측을 고르는 방식에서 충돌이 생길 수 있습니다. 표에서 A가 관측 1을 먼저 가져가면 B는 관측 2와 연결되어 총비용이 6.5가 됩니다. 반대로 A를 관측 2에, B를 관측 1에 연결하면 합계는 5입니다. Hungarian 알고리즘은 이처럼 전체 비용이 작도록 일대일 배정을 구합니다. 현재 구현은 연결하지 않는 선택지도 두고, 비슷한 후보가 경쟁하면 먼저 보류합니다. 다만 비용표에 대한 최적 배정이 실제 차량 신원의 정답을 보장하는 것은 아닙니다. 보정이나 탐지가 틀리면 잘못된 연결이 가능합니다.

### 화면 조작과 진행

숫자를 모두 읽기보다 두 조합의 합계 6.5와 5를 비교한다.

### 예상 질문

Hungarian이 차량을 인식하나? → 아니다. 위치 기반 비용표의 할당을 계산할 뿐이며 외형을 보지 않는다.

## 7페이지. CAM-2 관측을 기존 Global ID에 연결

### 그림과 기술 설명

현재 코드로 확인한 입력 예시다. CAM-1 t=0,.2,.4에 x=20,21,22, y=15를 관측하면 동일 ID가 3회 확인되어 TRACKED가 된다. 속도 평활화 결과 vx=4.55. CAM-2 t=.5의 x=22.6은 예상 x=22.455에서 .145cm 차이라 새 카메라 조건을 통과한다. 실제 CCTV 측정 결과가 아니다.

### 발표 대본

이제 두 카메라가 하나의 ID를 쓰는 과정을 보겠습니다. CAM-1에서 0초, 0.2초, 0.4초에 관측한 위치가 이동 조건을 통과하면 같은 ID에 연결되고, 세 번 확인되어 추적 상태가 됩니다. 이어 CAM-2가 0.5초에 22.6, 15 위치를 관측합니다. 기존 기록에서 예상한 x 좌표는 22.455이고 오차는 0.145센티미터이므로 새 카메라의 거리와 시간 조건을 통과합니다. 새 ID를 만드는 대신 기존 ID에 CAM-2 관측을 추가합니다. 서로 다른 시각의 좌표를 무조건 평균내지 않고, 카메라와 시각을 보존합니다. 이 표는 코드 동작을 설명하는 입력 예시이며 실제 두 카메라 검증 결과는 아닙니다.

### 화면 조작과 진행

마지막 행의 카메라는 바뀌지만 오른쪽 ID는 같다는 점을 강조한다.

### 예상 질문

두 카메라가 이미 서로 다른 ID를 만들면? → 현재 이미 생성한 ID끼리 소급 병합하는 기능은 없다.

## 8페이지. 누락과 불확실성을 상태로 관리

### 그림과 기술 설명

확인 횟수는 0.1초 이상 간격이 있는 관측으로 센다. 확정 차량은 마지막 관측에서 1.2초 초과 LOST, 4초 초과 REMOVED. 미확정 후보의 종료 기준은 1.5초다. 모호한 연결은 UNCERTAIN이며 상태 우선순위에 따라 오래된 관측은 LOST가 된다.

### 발표 대본

한 번 탐지하지 못했다고 바로 차량을 지우면 화면에서 ID가 계속 바뀝니다. 그래서 새 관측은 후보로 시작하고 반복 확인 뒤 확정합니다. 확정 차량이 잠시 보이지 않으면 마지막 위치를 유지하고, 마지막 관측 후 1.2초가 지나면 일시 소실, 4초가 지나면 종료로 전환합니다. 교차 등으로 연결 후보가 비슷하면 불확실 상태로 보류합니다. 사용자가 선택한 ID가 종료되어도 다른 차를 자동으로 선택하지 않습니다. 이 구조는 짧은 누락을 견디는 대신 긴 가림 이후의 동일 차량 복구를 보장하지 않습니다.

### 화면 조작과 진행

현재 값은 기본값이라고 말한다. 시연에서 손으로 가렸을 때 정확히 1.2초에 바뀐다고 단정하지 말고 분석·전송 간격도 있음을 유의한다.

### 예상 질문

반복 오탐도 차량으로 확정될 수 있나? → 그렇다. 후보 단계는 일회성 오탐을 줄이지만 탐지 오류를 완전히 해결하지 않는다.

## 9페이지. 이동 방향 회전과 위치 보간

### 그림과 기술 설명

11월 4일 추가. 같은 카메라의 연속 관측 간격이 .02~1.2초이고 변위가 .5cm 이상, 속도가 1cm/s 이상일 때 atan2(vx,-vy)로 시계 방향 각도를 갱신한다. heading(차체)은 null, motion_heading만 제공한다. 지도 좌표는 x 오른쪽, y 아래. 웹은 최단 각도로 350ms 보간한다.

### 발표 대본

아이콘이 항상 세로로 표시되던 부분도 수정했습니다. 같은 카메라의 이전 위치와 현재 위치 차이로 이동 방향을 구합니다. 지도 위쪽을 0도, 오른쪽을 90도로 두고 아이콘에 회전을 적용합니다. 0.5센티미터 이상의 이동과 초당 1센티미터 이상의 속도를 조건으로 두어 작은 흔들림에는 회전하지 않게 했습니다. 정지하면 마지막 방향을 유지합니다. 위치는 서버에서 평활화하고 브라우저에서 보간하며, 회전도 가장 짧은 각도로 연결합니다. 계산한 값은 이동 방향이므로 후진할 때 실제 차체 앞쪽과 다를 수 있습니다. 이 기능은 재학습이나 Homography 변경 없이 추가했습니다.

### 화면 조작과 진행

이동 방향과 차체 방향을 구분한다. 실제 시연에서는 작은 떨림 대신 분명한 좌우 이동을 보여준다.

### 예상 질문

## 10페이지. 분석과 웹 전송을 분리한 구조

### 그림과 기술 설명

TrackingBridge.publish가 상태를 만들고 StateStore에서 짧은 잠금으로 참조를 교체한다. API는 저장소만 읽는다. WS는 전체 상태를 즉시 전송하고 이후 .2초 간격의 루프로 반복한다. 송신 제한 2초, 누적 큐 없음. 느린 소비자 때문에 네트워크 대기로 추론을 막지 않는다.

### 발표 대본

웹 연결이 느려질 때 카메라 분석까지 기다리지 않도록 분석과 전송을 분리했습니다. 분석 스레드는 최신 상태 하나를 저장하고 API 서버는 그 상태를 읽어 보냅니다. 과거 데이터를 누적하지 않으므로 느린 클라이언트는 중간 상태를 건너뛰고 최신 상태를 받습니다. FastAPI가 레이아웃과 현재 상태를 제공하고 WebSocket이 상태를 반복 전달합니다. 새 접속에는 전체 상태를 바로 보내 복구를 단순하게 했습니다. 다만 추적과 직렬화 연산은 추가되므로 FPS 영향이 없다고 단정할 수는 없고 실제 측정이 필요합니다.

### 화면 조작과 진행

추론 경로와 네트워크 경로 사이 StateStore를 가리킨다.

### 예상 질문

왜 DB나 Firebase를 안 썼나? → 이번 범위는 로컬 최신 상태 전달이다. 영구 이력과 팀 앱 연동은 후속 범위다.

### 화면 조작과 진행

① Follow 클릭 ② 통로 방향으로 이동 ③ 2초 안팎 가림, LOST 표시 확인 ④ 4초 이상 가림, 종료 안내 확인 ⑤ 재등장 시 자동 선택하지 않는지 확인 ⑥ 전체 보기. 임계값보다 조금 여유 있게 기다린다. 두 카메라 시야 이동은 각각 독립 보정이 완료된 경우에만 추가한다.

## 15페이지. 보충: CNN의 은닉층은 몇 개인가?

### 그림과 기술 설명

ParkitTiny 인스턴스에서 Conv2d24, BatchNorm2d19, SiLU19개를 확인했다. 최종 출력 Conv 네 개를 제외하면 중간 합성곱20개다. 병렬 분기가 있어 모두 직렬은 아니다. 가장 긴 S8 경로는 출력 포함 Conv18개다.

### 발표 대본

은닉층 개수는 무엇을 층으로 세는지부터 정해야 합니다. 합성곱은 총24개로 Backbone12개, Neck4개, Head의 중간 특징 처리4개, 최종 출력4개입니다. 출력층을 제외하면 중간 합성곱층20개입니다. 정규화와 활성함수를 별도 연산층으로 세면 숫자는 달라지고, 분기 구조라서 모두 직렬로 통과하는 것도 아닙니다. 이 숫자는 데이터가 자동으로 정한 값이 아니라 코드에서 선택한 블록 수의 합입니다. S4와 S8에 각각 잔차 블록 하나, S16에 두 개, Neck에 하나를 배치했습니다. 이 개수가 최적이라는 비교 실험은 아직 없으므로 경량성과 특징 추출을 고려한 초기 설계라고 설명해야 합니다.

### 화면 조작과 진행

모델 깊이 질문 시 보충 슬라이드로 이동. 출력 제외 합성곱 기준20개라고 한정한다.

### 예상 질문

데이터가 늘면 은닉층도 늘어나나? → 아니며 같은 구조의 가중치가 바뀐다. 층 수를 바꾸려면 모델 구조를 수정해야 한다.

## 교수님 질문 대비: 설계 이유

**왜 호모그래피인가?** 고정 카메라와 평평한 매트, 알려진 기준점이라는 조건에서 바닥 좌표를 cm로 비교하기 위해 사용한다. 전체 3D 복원이 요구되지 않는다. 렌즈 왜곡이나 높이가 있는 차체의 점은 별도 오차 요인이며 바닥 접점도 근사값이다.

**왜 Hungarian인가?** 탐지 순서대로 가장 가까운 관측을 고르면 여러 차량이 경쟁한다. 허용된 후보의 전체 비용에 대해 일대일 할당을 구한다. 실제 차량 동일성까지 보장하는 알고리즘은 아니다.

**카메라 ID가 Global ID가 되는가?** 관측에는 카메라 ID가 그대로 남는다. 관측이 하나의 차량 기록에 연결되는 것이며 Global ID는 그 기록의 이름이다. 카메라별 별도 Local ID 추적기는 없다.

**시간을 왜 보존하나?** 시각이 다른 위치를 동시 관측처럼 평균내거나, 오래된 위치로 되돌리는 것을 막기 위해서다. 현재 호스트 수신 시각 기반이며 하드웨어 동기화가 아니다.

**현재 칼만 필터를 쓰나?** 아니다. 같은 카메라 관측으로 속도를 구하고 평활화한 속도로 예상 위치를 계산한다. 표시 위치에는 지수 평활화, 브라우저에는 위치·각도 보간을 사용한다.

**왜 Re-ID를 쓰지 않았나?** 이번 요구는 좌표 기반 첫 구현이다. 외형 모델에 필요한 데이터와 연산을 추가하지 않고 고정 매트 조건을 활용했다. 가까운 차량의 교차나 긴 가림에 한계가 있다.

**네트워크가 느리면?** 분석은 최신 스냅샷을 교체하고 전송은 API 스레드가 맡는다. 중간 상태가 누적되지 않는다. 새 계산 비용 자체는 추가되므로 실제 FPS 영향은 측정해야 한다.

**왜 Follow에서 지도가 회전하지 않나?** North-up 방식으로 지도 방향을 유지하고 viewBox만 이동한다. 차량 아이콘은 이동 방향으로 회전하지만 차체 방향 추정과 구분한다.

**왜 은닉층 20개인가?** Backbone12+Neck4+Head중간4의 합이다. 최종 출력 Conv4를 포함하면24다. S4·S8에 각각 잔차 Block 하나, S16에 두 개, Neck에 하나를 코드로 선택했다. 이것이 최적이라는 ablation 비교는 아직 없다.

## CNN 계수 기준 상세

| 부분 | 합성곱 수 | 계산 |
|---|---:|---|
| Stem | 1 | 일반 3×3 Conv |
| S4 | 3 | 다운샘플 Conv1 + 잔차 Block의 depthwise1·pointwise1 |
| S8 | 3 | 다운샘플 Conv1 + Block2 |
| S16 | 5 | 다운샘플 Conv1 + Block 두 개의 Conv4 |
| Neck lateral | 1 | 채널 축소 1×1 Conv |
| Neck fuse | 3 | 결합 후 Conv1 + Block2 |
| Head 중간 | 4 | S8·S16 각각 obj·box 분기의 Conv1씩 |
| Head 출력 | 4 | S8·S16 각각 obj1채널·box4채널 출력 Conv1씩 |

합계 Conv24, BatchNorm19, SiLU19다. 이는 등록된 모듈 수이며 모든 모듈을 직렬로 통과한다는 뜻은 아니다. 가장 긴 입력→S8 출력 경로의 합성곱은 출력 포함18개다. stride8/16은 특징 맵의 공간 축소 배율로 은닉층 수가 아니다. width16은 채널 폭의 기준으로 층 수와 다르다. 학습 데이터가 늘어나도 구조가 같으면 층 수는 같고 가중치가 바뀐다.
