# PARKIT 11월 3일 작업 발표: 슬라이드 설명과 대본

기준: 2026년 11월 3일 구현·검증 기록. 총 10장, 약 7~9분 분량. 화면은 실제 구현물의 **합성 데모 캡처**이며 실제 CCTV 성능 측정 결과가 아닙니다.

## 1페이지. PARKIT 2D 실시간 차량 추적

### 슬라이드 설명

이번 발표의 범위는 2026년 11월 3일 구현 기록에 남아 있는 차량 추적과 웹 지도 확장이다. 모델 재학습이나 새 탐지 모델 개발을 이번 작업의 성과로 설명하지 않는다.

### 발표 대본

어제는 기존 PARKIT 주차면 점유 판정 프로그램에 차량 추적과 2D 웹 화면을 연결했습니다. 기존에는 어느 칸이 비었는지를 보여줬다면, 이번에는 차량마다 ID를 부여하고 지도에서 차량을 선택해 따라갈 수 있도록 확장했습니다. 오늘은 기존 프로그램과 어떻게 연결했는지, 차량 ID를 어떤 기준으로 유지하는지, 그리고 어디까지 검증했는지 설명드리겠습니다.

## 2페이지. 기존 점유 판정과 차량 추적의 연결

### 슬라이드 설명

상단은 기존 탐지와 좌표 변환이다. 결과가 아래 두 경로로 나뉜다. 주차면 상태를 관리하는 기존 Tracker와 차량 ID를 관리하는 VehicleTracker는 서로 다른 객체다. 점유 알고리즘을 교체하지 않고 새 처리 경로를 덧붙였다.

### 발표 대본

카메라 영상은 기존 YOLO 또는 PARKIT Tiny 모델로 탐지합니다. 기존 judge_frame 함수에서 탐지 상자의 접점을 매트 좌표로 바꾼 뒤 결과를 두 경로로 사용합니다. 왼쪽은 기존 주차면 상태 관리이고, 오른쪽이 이번에 추가한 차량 추적입니다. 기존 Tracker는 주차면이 비었는지 관리하고, 새 VehicleTracker는 어떤 차량이 어디로 이동했는지 관리합니다. 두 결과를 최신 상태 저장소에 모아 API를 통해 웹 화면에 전달합니다. 따라서 차량 추적을 추가하기 위해 기존 점유 판정 알고리즘을 바꾸지는 않았습니다.

## 3페이지. 두 카메라를 연결하는 공통 좌표

### 슬라이드 설명

카메라별 픽셀 좌표는 서로 비교할 수 없다. 각 카메라의 기존 Homography로 같은 매트 cm 좌표계에 옮긴다. 좌표뿐 아니라 camera_id와 observed_at를 보존한다. 현재는 별도 Local ID를 먼저 만든 뒤 병합하는 구조가 아니다.

### 발표 대본

두 카메라에서는 같은 차량도 화면의 다른 픽셀 위치에 나타납니다. 그래서 각 카메라를 보정하고, 탐지 상자의 아래쪽 중앙 접점을 같은 매트의 센티미터 좌표로 변환합니다. 이렇게 변환한 좌표와 관측 시간을 비교해서 같은 차량으로 연결할 수 있는지 판단합니다. 카메라 ID와 시각도 함께 보존하므로 늦게 들어온 관측을 무조건 현재 위치처럼 합치지 않습니다. 현재 구현은 카메라별 Local ID를 별도로 만든 뒤 합치는 방식이 아니라, 공통 좌표의 관측을 Global ID에 직접 연결하는 방식입니다. 실제 두 카메라에서의 정확도는 추가 검증이 필요합니다.

## 4페이지. Global ID 매칭과 추적 상태

### 슬라이드 설명

위쪽은 매칭 과정, 아래쪽은 대표적인 상태 흐름이다. Hungarian 알고리즘은 허용된 후보 안에서 일대일 할당을 구한다. 단순히 매 프레임 가장 가까운 차량을 무조건 붙이지 않는다. 3회 확인은 서로 충분히 떨어진 시각의 관측을 의미한다. LOST 1.2초와 REMOVED 4초는 마지막 관측부터의 기본값이다.

### 발표 대본

차량 ID는 이전 위치와 현재 위치의 거리, 시간 간격, 최대 이동 속도를 함께 고려해서 연결합니다. 이동할 수 없는 거리의 후보는 제외하고, 허용된 후보에 일대일 할당을 적용합니다. 여러 후보가 비슷하게 가까우면 확정 연결을 보류하고 불확실 상태를 표시합니다. 새 차량은 후보로 시작하고, 서로 다른 시각에 세 번 확인하면 추적 상태가 됩니다. 마지막 관측 후 1.2초가 지나면 일시 소실, 4초가 지나면 종료 상태로 전환합니다. 이 값들은 초기 기본값이며 실제 미니카 속도와 탐지 간격에 맞게 조절해야 합니다. 외형을 확인하는 Re-ID는 사용하지 않아 완전한 가림 이후 동일성을 보장하지는 않습니다.

## 5페이지. 전체 주차장 화면

### 슬라이드 설명

2026년 11월 3일 저장한 실제 웹 구현 화면이다. 입력과 주차면 색은 합성 데모이므로 실제 탐지 성공 화면으로 소개하면 안 된다. 56개 칸의 배치는 기존 SlotTable을 사용한다. 회색은 STATIC_BLIND이며 실제로는 정적 가림/감시 불가 상태를 의미한다.

### 발표 대본

화면은 React와 SVG로 구현했습니다. 기존 주차장 레이아웃 데이터를 재사용해서 56개 주차면을 표시하고, 점유 상태를 색으로 구분합니다. 초록색은 빈자리, 빨간색은 점유, 노란색은 동적 가림, 회색은 정적 가림 상태입니다. 차량에는 ID를 표시하고 클릭하면 파란색으로 강조합니다. 지금 보이는 캡처는 실제 구현된 웹 화면에 합성 데이터를 넣어 확인한 결과입니다. 따라서 화면에 보이는 차량 위치나 주차면 색을 실제 CCTV의 판정 결과로 해석하면 안 됩니다.

## 6페이지. 선택 차량을 따라가는 Follow 모드

### 슬라이드 설명

선택 차량을 화면 중심에 유지하도록 SVG viewBox를 이동한다. 지도 방향은 North-up으로 고정하며 실제 차체 방향을 표현하지 않는다. 서버는 좌표 평활화, 프런트는 약 350ms 보간을 사용한다. 두 캡처의 시간은 다르므로 동일 프레임 전후 비교는 아니다.

### 발표 대본

차량을 선택하고 따라가기 버튼을 누르면 선택한 차량이 화면 중심에 유지되고 주변 지도가 움직입니다. 지도는 위쪽 방향을 고정한 North-up 방식입니다. 위치 갱신 사이를 보간해서 이동이 부드럽게 보이게 했습니다. 차량이 잠시 가려지면 마지막 관측 위치와 추적 상태를 보여주고, ID가 끊겼다고 다른 차량을 자동으로 선택하지 않습니다. 연결이 끊기면 화면에 알리고 자동 재연결합니다. 이 화면의 자동차 모양은 접점 좌표에 놓은 근사 표식이므로 실제 차체의 중심이나 방향과 완전히 일치하는 것은 아닙니다.

## 7페이지. 실제 카메라 실행과 합성 데모

### 슬라이드 설명

같은 웹 주소라도 실행한 Python 프로그램에 따라 데이터 출처가 달라진다. tracking_demo.py는 occupancy.py의 결과를 읽는 프로그램이 아니라 관측값을 직접 생성한다. occupancy.py --web은 설정한 실제 카메라 또는 영상 입력의 분석 결과를 전달한다.

### 발표 대본

실행 방법에 따라 웹 화면의 데이터 출처가 달라집니다. occupancy.py를 web 옵션과 함께 실행하면 설정된 카메라나 영상의 실제 분석 결과가 웹으로 전달됩니다. 반면 tracking_demo.py는 카메라를 열지 않고 가짜 관측과 예시 점유 상태를 생성합니다. 데모는 카메라 없이 화면과 연결, 차량 선택 동작을 시험하기 위해 만든 것입니다. 두 프로그램이 같은 웹 주소를 사용하기 때문에 주소만 보고 실제 분석인지 판단할 수는 없습니다. 실제 시연에서는 occupancy.py를 실행하고 카메라와 모델 설정을 확인해야 합니다.

## 8페이지. 주요 구현 파일

### 슬라이드 설명

2026년 11월 3일 작업 기록 기준으로 기존 실행 코드 변경은 occupancy.py이며 README에는 안내 링크를 추가했다. 신규 모듈은 추적, 연결, API, 웹 화면으로 역할을 나눈다. 표는 주요 파일만 보여준다.

### 발표 대본

파일은 역할별로 나눴습니다. occupancy.py에는 기존 분석 결과를 새 기능에 전달하고 웹 서버를 켜는 연결 부분을 추가했습니다. vehicle_tracker.py는 ID 매칭과 누락 상태를 관리합니다. tracking_bridge.py는 기존 결과를 추적 입력으로 바꾸고 최신 상태를 저장합니다. parking_api.py는 HTTP와 WebSocket으로 상태를 전달하고, web 폴더는 React 화면입니다. 네트워크 전송은 분석 스레드와 분리하고 최신 상태 하나만 저장해서, 웹 클라이언트가 느려져도 오래된 상태가 계속 쌓이지 않도록 했습니다.

## 9페이지. 11월 3일 검증 결과

### 슬라이드 설명

기존 기하 35/35, 기존 파이프라인 33/33은 변경 전후 통과 기록이다. 추적 15개, API/Engine 5개, 프런트 5개는 각각 통과한 테스트 수다. 리플레이 1개에서 추적 off/on/20배속의 상태 변경 107행이 일치했다. 107은 차량 수나 정확도 백분율이 아니다.

### 발표 대본

기존 기능이 유지되는지 먼저 확인했습니다. 기하 테스트 35개와 기존 파이프라인 테스트 33개가 변경 전후 모두 통과했습니다. 새 차량 추적 테스트 15개, API와 Engine 통합 테스트 5개, 프런트엔드 테스트 5개도 통과했습니다. 같은 합성 영상을 사용한 리플레이 시험에서는 추적을 끄거나 켜거나 재생 속도를 바꿔도 기존 점유 상태 변경 107행이 같았습니다. 브라우저에서 선택과 Follow, 연결 복구도 확인했습니다. 다만 이것은 기능과 회귀 검증 결과이고, 실제 CCTV의 인식률이나 ID 유지율을 측정한 결과는 아닙니다.

## 10페이지. 실제 CCTV 검증 계획

### 슬라이드 설명

다음 작업은 두 카메라 보정 일치 여부와 접점 오차 측정, 교차/가림 시 ID 유지, 웹 활성화 전후 성능 측정이다. 주차된 차량 아이콘이 칸 밖으로 보이는 경우 보정 좌표·탐지 접점·아이콘 중심 기준을 먼저 분리해 확인한다. 임의로 그림만 이동시키면 좌표 오류를 감출 수 있다.

### 발표 대본

다음 단계는 실제 두 카메라를 고정하고 같은 매트 기준점으로 보정하는 것입니다. 같은 차량을 두 카메라가 볼 때 좌표가 얼마나 다른지 먼저 측정하겠습니다. 그다음 차량의 시야 이동과 교차, 일시 가림에서 ID가 유지되는지 확인하고, 웹을 켰을 때의 FPS와 지연도 비교하겠습니다. 주차된 차량 아이콘이 칸 밖에 걸치는 현상은 탐지 접점과 실제 차체 중심의 차이, 보정 오차, 아이콘 배치를 나누어 점검해야 합니다. 이번 작업에서는 기존 점유 판정을 보존하면서 차량 추적과 웹 지도를 연결했고, 실제 환경 검증을 다음 단계로 남겨두었습니다.

## 시연 준비

PARKIT 폴더에서 아래 명령을 실행하고 브라우저로 http://127.0.0.1:8765 를 엽니다.

실제 카메라 분석(보정·모델·카메라 설정 필요):

```bash
.venv-gui/bin/python runs/occupancy/occupancy.py --web
```

```bash
.venv-gui/bin/python runs/occupancy/tracking_demo.py
```

두 실행은 같은 포트를 쓰므로 동시에 실행하지 않습니다. Ctrl+C로 종료합니다. 발표 순서는 전체 지도 확인, 차량 선택, 따라가기, 전체 지도로 돌아가기입니다. 합성 데모 시연에서는 가짜 입력임을 먼저 설명합니다.

## 예상 질문에 대한 짧은 답변

**탐지와 추적의 차이는?** 탐지는 현재 프레임에서 차량 위치를 찾고, 추적은 시간에 걸쳐 관측을 연결해 ID를 유지합니다.

**어제 새 모델을 학습했나?** 이번 범위는 기존 YOLO/PARKIT Tiny의 탐지 결과를 이용한 추적과 웹 표시 확장입니다. 새 학습 성과로 발표하지 않습니다.

**두 카메라에서 같은 차라는 것을 어떻게 아나?** 공통 매트 좌표, 시간 차이, 이동 가능한 범위를 비교해 추정 연결합니다. 외형이나 번호판 확인이 없어 동일성을 보증할 수는 없습니다.

**Local ID와 Global ID를 둘 다 쓰나?** 현재 별도 카메라별 Local ID 추적기는 없고 camera_id가 붙은 관측을 Global ID에 직접 연결합니다.

**주차돼 있는데 아이콘이 칸 밖으로 나오는 이유는?** 표시 위치가 탐지 상자 접점이고 아이콘을 그 점 중심으로 그리기 때문일 수 있습니다. Homography 보정과 탐지 접점 오차도 함께 확인해야 하며, 웹 그림만의 문제라고 단정할 수 없습니다.

**모든 교차에서 ID가 유지되나?** 합성 시나리오를 시험했지만 일반적인 보장은 없습니다. 위치가 모호하면 연결을 보류하고 불확실 상태를 표시합니다.

**107행 일치가 100% 정확도인가?** 아닙니다. 동일 합성 입력에서 기존 점유 상태 변경 기록이 보존됐다는 회귀 검증 결과입니다.
