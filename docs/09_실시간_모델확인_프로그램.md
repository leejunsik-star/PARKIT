# 09. 실시간 모델 확인 프로그램 사용법 (2026-10-17)

웹캠 화면을 받아 고른 모델로 계속 분석하는 프로그램이다. 창 왼쪽에는 웹캠 화면과 차량 상자를, 오른쪽 패널에는 옵션과 결과를 보여준다. 모델, 입력 크기, 신뢰도 기준, 입력(웹캠/영상)을 모두 마우스로 바꿀 수 있어, 같은 장면에서 모델별 차이를 바로 비교할 수 있다. 결과는 패널의 결과 칸과 콘솔에 함께 한 줄씩 나온다.

- 파일: `docs/도구/live_detect.py`
- 화면 예시: `docs/도구/live_detect_예시.jpg` (녹화 영상 한 장면, RT-DETR-L 결과)

## 설치 (한 번만)

명령 프롬프트(cmd)에서 차례로 실행한다.

```
pip install ultralytics
pip install "opencv-python==4.10.0.84"
pip install effdet
```

- 두 번째 줄은 반드시 ultralytics 다음에 실행한다. OpenCV 5.0은 이 웹캠을 열지 못했다(웹캠 점검 때 확인).
- `effdet`은 EfficientDet-D2를 쓸 때만 필요하다.
- 창 화면은 파이썬에 기본으로 들어 있는 tkinter를 쓴다. python.org 설치 파일로 기본 설치했다면 따로 설치할 것이 없다.
- NVIDIA 그래픽카드가 있으면 PyTorch GPU 버전을 따로 설치해야 GPU를 쓴다. 없으면 CPU로 돈다. 프로그램 시작 시 콘솔 첫 줄에 계산 장치(cpu 또는 cuda)가 나온다.

## 실행

`docs/도구` 폴더에서 `python live_detect.py`를 실행하면 창이 뜨고 웹캠 0번, YOLO26n으로 바로 분석을 시작한다. 카메라 앱 등 웹캠을 쓰는 다른 프로그램은 먼저 닫는다.

## 오른쪽 패널

| 칸 | 기능 |
|---|---|
| 입력 | 웹캠 번호(0~4)와 해상도(640×480, 1280×720, 1920×1080) 또는 영상 파일(찾기...)을 고른 뒤 **이 입력으로 열기**. 영상이면 화면 아래에 재생 막대가 생김(아래 참고) |
| 모델 | 목록에서 고르면 바로 바뀜. 처음 고르는 모델은 내려받느라 잠시 걸림. **입력 크기**는 모델마다 기본값으로 바뀌며 직접 바꿀 수도 있음. **모델 파일 불러오기...**로 다른 위치의 .pt 파일을 골라 목록에 더할 수 있음(아래 "학습한 모델 쓰기") |
| YOLOE 프롬프트 | YOLOE 모델을 골랐을 때만 켜짐. 찾을 대상을 쉼표로 적고 **프롬프트 적용** |
| 탐지 기준 | **신뢰도 기준** 슬라이더(0.05~0.95). **차량이 아닌 물체도 보기**를 켜면 다른 물체를 주황색 상자로 표시 |
| 실행 | **분석 빈도**(제한 없음, 초당 10·5·2·1회, 2초에 1회, 5초에 1회, 기본 초당 2회), **CPU 코어**(모델 계산에 쓸 코어 수, 기본은 전체의 절반), **분석 일시정지**, **결과를 CSV로 기록**(같은 폴더 `live_log_날짜.csv`, 맨 끝 열은 프레임번호), **현재 화면 저장**(상자 포함 jpg) |
| 결과 | 분석할 때마다 한 줄씩 추가. 최근 400줄 유지 |

창 아래 줄에는 현재 모델, 입력 크기, 프레임당 시간, 차량 수가 나온다.

## 영상 재생 막대 (영상 파일 입력일 때만)

영상 파일을 열면 화면 바로 아래에 재생 막대가 나타난다. 웹캠으로 바꾸면 사라진다.

| 버튼 | 기능 |
|---|---|
| 정지 / 재생 | 영상을 멈추거나 다시 재생. 멈춘 동안에는 같은 장면을 다시 분석하지 않음 |
| 처음 | 첫 프레임으로 이동 |
| -5초 / +5초 | 5초 뒤로 / 앞으로 이동 |
| ◀ 1프레임 / 1프레임 ▶ | 영상을 멈추고 한 프레임씩 이동. 여러 번 누르면 누른 만큼 이동 |
| 재생 막대 | 끌어서 놓은 위치로 이동. 오른쪽에 현재 시간 / 전체 길이 표시 |
| 반복 | 켜면 끝나고 처음부터 다시 재생(기본). 끄면 끝에서 멈추고, 그때 **재생**을 누르면 처음부터 다시 재생 |

위치를 옮기면 그 장면을 바로 분석해 상자가 새 장면에 맞게 바뀐다. 멈춘 장면에서 모델이나 신뢰도 기준을 바꿔 가며 같은 장면의 결과를 비교할 때 쓴다. 1080p 영상은 먼 곳으로 이동할 때 0.3초 정도 걸릴 수 있다.

## 시작 옵션 (선택)

창에서 다 바꿀 수 있으므로 보통은 필요 없다. 시작 상태를 정해 두고 싶을 때만 쓴다.

| 옵션 | 뜻 |
|---|---|
| `--cam 1` | 시작 웹캠 번호 (기본 0) |
| `--model rtdetr` | 시작 모델 (yolo26n, rtdetr, oiv7, yoloe-s, effdet, best 등) |
| `--weights 경로\best.pt` | 다른 위치의 모델 파일로 시작 |
| `--source 영상.mp4` | 웹캠 대신 녹화 영상으로 시작 |
| `--conf 0.3` | 시작 신뢰도 기준 (기본 0.25) |
| `--rate 1` | 시작 분석 빈도, 초당 횟수 (0이면 제한 없음, 기본 2) |
| `--threads 2` | 모델 계산에 쓸 CPU 코어 수 (기본: 전체의 절반) |
| `--prompt "toy car,car"` | YOLOE 시작 프롬프트 |
| `--log` | 처음부터 CSV 기록 |
| `--width 1920 --height 1080` | 시작 웹캠 해상도 (기본 1280×720, MJPEG) |
| `--nogui` | 창 없이 콘솔 출력만 |
| `--dual` | 카메라 2개로 시작 (아래 "카메라 2대 보기") |
| `--cam2 1` | 카메라 2의 웹캠 번호 (기본 1) |
| `--source2 영상.mp4` | 카메라 2에 웹캠 대신 영상 |
| `--model2 best`, `--weights2 경로` | 카메라 2(모델 비교면 모델 B)의 시작 모델 (기본: 카메라 1과 같음) |
| `--compare` | 모델 비교로 시작. `--model`이 A, `--model2`가 B (아래 "모델 비교") |

## 학습한 모델 쓰기 (2026-10-27 추가)

Colab에서 학습한 `best.pt`를 두 가지 방법으로 쓸 수 있다.

1. **이 폴더에 두기**: `best.pt`를 `docs/도구` 폴더(live_detect.py와 같은 곳)에 넣고 목록에서 **학습 모델(best.pt)**을 고른다. 시작부터 쓰려면 `python live_detect.py --model best`.
2. **다른 위치에서 불러오기**: 모델 칸의 **모델 파일 불러오기...**를 눌러 .pt 파일을 고르면 목록 맨 아래에 더해지고 바로 그 모델로 바뀐다. 시작부터 쓰려면 `python live_detect.py --weights 경로\best.pt`.

- 목록에 보이는 이름은 `runs\pilot_v1\weights\best.pt`라면 `pilot_v1_best`처럼 학습 이름을 따서 붙는다. 같은 이름이 결과 줄, CSV 기록, 화면 저장 파일 이름에 쓰인다.
- 입력 크기는 학습 때와 같은 640으로 시작한다.
- 차량으로 세는 기준: 모델 클래스 중 car·bus·truck·vehicle. 이 이름이 하나도 없는 모델이면 모든 클래스를 차량으로 센다. 우리 모델은 `car` 하나뿐이다.
- 파일이 없거나 불러오기에 실패하면 결과 칸에 이유가 나오고 YOLO26n으로 돌아간다. 목록 표시도 YOLO26n으로 바뀐다.
- Ultralytics로 학습한 YOLO 계열 .pt 파일용이다. RT-DETR·YOLOE 파일은 기존 목록 항목으로 쓴다.
- **직접 만든 PARKIT Tiny 모델(mymodel.pt)**: Ultralytics 형식이 아니어도 같은 방법(모델 파일 불러오기..., `--weights`)으로 불러온다. 파일 안에 `stem.0.weight` 같은 가중치만 들어 있으면 이 모델로 알아보고, 구조는 가중치 파일과 같은 폴더(없으면 live_detect.py 폴더)의 `model.py`에서 가져온다. 구조를 바꿔 다시 학습하면 새 `model.py`도 같은 폴더에 둔다. PyTorch가 필요하다.
  - 전처리: 학습 코드가 없어 test 사진 6장(정답 상자 122개)에 여러 방식을 넣어 비교했다. 가운데 letterbox(회색 114), RGB, 0~1 방식이 정답과 가장 잘 맞아(재현율 0.91, 평균 IoU 0.83) 이것을 쓴다. 학습 코드가 다르게 했다면 맞춰 고쳐야 한다.
  - 같은 test 사진에서 신뢰도 기준별 결과: 0.25면 재현율 0.91·오검출 89개, 0.4면 0.84·21개, 0.5면 0.77·5개. 오검출이 많아 기준을 0.4~0.5로 올려 쓰는 편이 낫다. 주차판 밖 장면(종이 도면)에서는 기준 0.25에서 상자가 50개 넘게 나왔다.
- 시험: 클라우드에서 콘솔 모드로 `--model best`와 `--weights`를 실행해 불러오기와 차량 수가 나오는 것을 확인했다. 창은 가상 화면에서 가짜 모델로 파일 고르기, 목록 추가, 실패 시 되돌아가기를 확인했다.

## PyTorch가 막힌 PC에서 쓰기 (2026-10-27 추가)

학교 PC에서 `import torch`가 `WinError 4551 애플리케이션 제어 정책에서 이 파일을 차단했습니다`로 실패했다. 학교 보안 정책이 PyTorch 파일을 막는 것이라 코드로는 풀 수 없다. 이런 PC에서는 YOLO26n 등 기존 목록 모델도 쓸 수 없고, ONNX로 바꾼 학습 모델만 쓸 수 있다. ONNX 모델은 이미 웹캠에 쓰는 OpenCV만으로 돌아간다.

1. Colab에서 `best.pt`를 ONNX로 바꾼다(GPU 필요 없음).
   ```
   from google.colab import drive
   drive.mount('/content/drive')
   !pip install -q ultralytics onnx onnxslim
   !yolo export model=/content/drive/MyDrive/parkit_runs/pilot_v1/weights/best.pt format=onnx imgsz=640
   ```
2. 같은 `weights` 폴더에 생긴 `best.onnx`를 받아 `docs/도구` 폴더에 넣는다.
3. `python live_detect.py --model best-onnx`로 실행하거나, 목록에서 **학습 모델 ONNX(best.onnx)**를 고른다. 다른 위치의 .onnx 파일은 **모델 파일 불러오기...**로 고른다.

- 시작 모델(기본 YOLO26n)을 불러오지 못하면 한 번 알리고 분석을 멈춘다. 그때 목록에서 ONNX 모델을 고르면 된다.
- 입력 크기는 내보낼 때 정한 640으로 고정이다. 입력 크기 목록을 바꿔도 적용되지 않는다.
- `nms=True`로 내보낸 파일은 OpenCV가 읽지 못한다. 위 명령(기본값)대로 내보낸다.
- 결과는 Ultralytics로 같은 ONNX 파일을 돌린 결과와 거의 같았다(사진 3장, 상자 수 같음, 상자 IoU 평균 0.99 이상). 다만 .pt를 직접 돌릴 때와는 상자가 한두 개 다를 수 있다. YOLO26의 .pt는 NMS 없는 출력을 쓰고, ONNX 기본 내보내기는 NMS를 거치는 출력을 쓰기 때문이다.
- 속도(클라우드 CPU, 640): 코어 2개에서 PyTorch 약 48ms, OpenCV ONNX 약 135ms. 코어 4개에서 약 58ms, 약 69ms. PyTorch가 되는 PC(집 PC 등)에서는 지금처럼 `best.pt`를 쓰는 편이 빠르다.

## 카메라 2대 보기 (2026-10-27 추가)

오른쪽 패널 맨 위 **공통** 칸의 **보기**에서 **카메라 2개**를 고르면 왼쪽에 카메라 1과 카메라 2 화면이 위아래로 나온다. 시작부터 켜려면 `python live_detect.py --dual`.

- 패널의 **카메라 1**, **카메라 2** 탭이 각 카메라의 설정이다. 입력(웹캠 번호, 해상도, 영상 파일), 모델, 입력 크기, 신뢰도 기준, 분석 빈도, 일시정지, CSV 기록, 화면 저장을 카메라마다 따로 정한다. 카메라 2 탭은 2개 보기를 켰을 때만 열린다.
- 예: 카메라 1은 학습 모델, 카메라 2는 YOLO26n으로 두고 같은 장면을 비교할 수 있다. `python live_detect.py --dual --model best --model2 yolo26n`
- 카메라 2는 기본으로 웹캠 1번을 연다. 두 탭에서 같은 웹캠 번호를 고르면 열지 않고 결과 칸에 알려 준다.
- **CPU 코어**는 프로그램 전체에 한 값이라 공통 칸에 있다. 카메라 2대면 분석을 두 번 하므로 CPU 사용률이 약 두 배가 된다. 무거우면 분석 빈도를 낮춘다.
- 결과 칸에는 줄 앞에 `[카메라1]`, `[카메라2]`가 붙는다. CSV 기록은 `live_log_cam1_날짜.csv`, `live_log_cam2_날짜.csv`로, 화면 저장은 `live_cam1_모델_날짜.jpg`처럼 따로 저장된다.
- **카메라 1개**로 돌아가면 카메라 2 입력을 닫고 화면 하나로 돌아간다.
- 같은 USB 허브에 1920×1080 웹캠 2대를 꽂으면 대역폭이 모자라 한 대가 안 열릴 수 있다(추정). 그러면 해상도를 1280×720으로 낮추거나 다른 USB 포트에 꽂는다.
- 시험: 클라우드 가상 화면에서 영상 2개로 2개 보기 켜기·끄기, 카메라마다 다른 모델, 실패 시 YOLO26n으로 돌아가기를 확인했다(창 시험은 가짜 모델). 콘솔 모드에서는 실제 모델 2개(YOLO26x, YOLO11x)를 동시에 돌려 두 카메라 결과가 따로 나오는 것을 확인했다. 실제 웹캠 2대는 PC에서 확인이 필요하다.

## 모델 비교 (2026-10-27 추가)

웹캠 1대의 **같은 프레임**을 모델 A와 모델 B로 각각 분석해 위아래로 보여 준다. 공통 칸 **보기**에서 **모델 비교**를 고른다. 시작부터 켜려면 `python live_detect.py --compare --model yolo26n --model2 best`.

- 위 화면이 모델 A, 아래 화면이 모델 B다. 패널의 **모델 A (입력)** 탭에서 입력(웹캠·영상)과 A의 모델·옵션을, **모델 B** 탭에서 B의 모델·옵션을 고른다. B 탭의 입력 칸과 분석 빈도는 A를 그대로 따르므로 잠긴다.
- 두 모델은 A가 분석한 그 프레임을 B가 이어서 분석하고, 둘 다 끝난 뒤에 다음 프레임으로 넘어간다. 그래서 두 결과는 항상 같은 그림에 대한 것이며, 상태 줄의 **프레임** 번호(상자를 낸 프레임)로 확인할 수 있다. 두 모델이 번갈아 돌기 때문에 **분석 1회 ms**도 서로 방해받지 않은 값이다.
- 화면은 카메라 1개 모드처럼 실시간 영상에 마지막 결과 상자를 겹쳐 그린다. A의 상자는 B가 같은 프레임을 끝낼 때까지 기다렸다가 함께 바뀐다. 그래서 상자는 A와 B 분석 시간의 합만큼 늦게 따라온다(영상 자체는 늦지 않음).
- 신뢰도 기준은 탭마다 따로 정할 수 있다. 공정하게 비교하려면 두 탭을 같은 값으로 둔다.
- **현재 화면 저장**을 누르면 A와 B를 좌우로 붙인 한 장(`live_compare_A모델_vs_B모델_날짜.jpg`)으로 저장한다. 실시간 영상이 아니라 두 모델이 실제로 분석한 그 프레임에 상자를 그려 저장하므로, 차가 움직여도 상자가 어긋나지 않는다.
- 결과 칸의 줄 앞에 `[A]`, `[B]`가 붙는다. CSV 기록은 `live_log_A_날짜.csv`, `live_log_B_날짜.csv`로 나뉘며, 맨 끝 **프레임번호** 열이 같은 줄끼리 같은 프레임의 결과다.
- 시험: 클라우드 가상 화면에서 영상 파일로 YOLO26n ONNX와 학습 모델 ONNX를 비교해 두 화면의 프레임 번호가 항상 같은 것을 확인했고, 보기 방식(1개, 2개, 비교)을 오가며 오류가 없는 것을 확인했다. 콘솔 모드에서도 실제 .pt 모델 2개로 A와 B가 번갈아 같은 프레임을 분석하는 것을 확인했다. 실제 웹캠은 PC에서 확인이 필요하다.

## 결과 출력 예시

분석이 끝날 때마다 결과 칸과 콘솔에 한 줄씩 나온다. 첫 줄은 모델을 처음 불러오느라 느리다.

```
11:01:00 [RT-DETR-L 1280]   2169ms  차량 1대  car:0.92  (기타: person:0.62)
11:01:02 [RT-DETR-L 1280]   2016ms  차량 1대  car:0.88
```

## 동작 방식

- 웹캠 읽기와 모델 분석을 따로 돌린다. 화면은 웹캠 속도대로 계속 움직이고, 상자는 마지막 분석 결과를 겹쳐 그린다. 그래서 무거운 모델(RT-DETR 등)을 써도 화면이 밀리지 않는 대신, 상자가 차를 늦게 따라온다.
- 분석은 항상 가장 최근 프레임으로 한다. 밀린 프레임을 쌓아 두지 않는다.

## CPU 사용량 줄이기

분석을 쉬지 않고 계속하면 CPU를 거의 다 쓴다. 주차 칸 점유 판단은 초당 1~2회면 충분하므로 **분석 빈도**를 낮추는 것이 가장 효과가 크다. **CPU 코어**를 줄이면 사용률은 내려가지만 한 번 분석이 그만큼 느려진다.

클라우드(CPU 4코어)에서 녹화 영상으로 잰 값. 사용률은 코어 1개를 100%로 본 값이며, 1080p 영상 파일을 푸는 몫(약 40~50%)이 포함되어 있다.

| 모델 | 분석 빈도 | 코어 | CPU 사용률 | 분석 1회 |
|---|---|---|---|---|
| YOLO26n·640 | 제한 없음 | 4 | 약 330% | 약 55ms |
| YOLO26n·640 | 초당 2회 | 4 | 약 80% | 약 65ms |
| YOLO26n·640 | 초당 1회 | 4 | 약 60% | 약 60ms |
| YOLO26m·1280 | 제한 없음 | 4 | 약 370% | 약 1.0초 |
| YOLO26m·1280 | 제한 없음 | 1 | 약 140% | 약 1.9초 |
| YOLO26m·1280 | 초당 1회 | 2 | 약 230% | 약 1.1초 |

무거운 모델은 분석 1회가 1초 가까이 걸려 초당 1회로 제한해도 거의 쉬지 않으므로, 코어 수를 함께 줄이거나 가벼운 모델을 써야 한다.

## 시험 결과 (클라우드, CPU 4코어)

- 분석 부분: 웹캠 대신 `1_도색X.mp4`로 실행해 YOLO26n, RT-DETR-L, Open Images YOLOv8m, YOLOE-11s, EfficientDet-D2가 모두 불러와지고 결과가 나오는 것을 확인했다. 프레임당 시간은 YOLO26n 약 55ms, YOLOE-11s 약 130~200ms, Open Images 약 240ms, EfficientDet 약 1초, RT-DETR 약 2초였다.
- 창 부분: 가상 화면에서 창을 띄워 모델 바꾸기, 신뢰도 슬라이더, 다른 물체 보기 체크를 자동으로 조작해 결과 칸과 상자가 바뀌는 것을 확인했다. 이 시험은 클라우드 사정상 실제 모델 대신 고정 결과를 내는 가짜 모델로 했다(예시 이미지의 상자는 그 장면의 실제 RT-DETR 결과를 넣은 것).
- 재생 막대(2026-10-18): 가상 화면에서 `1_도색X.mp4`(923프레임)로 정지, 한 프레임 앞뒤(세 번 연속 누르기 포함), ±5초, 중간 위치 이동, 처음으로, 반복을 끈 채 끝까지 재생 후 다시 재생을 자동으로 눌러 위치가 맞게 바뀌는 것을 확인했다.
- 웹캠 연결과 Windows에서의 창 모양은 PC에서 확인이 필요하다.
