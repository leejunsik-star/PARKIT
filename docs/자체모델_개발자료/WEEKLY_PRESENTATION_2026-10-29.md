# PARKIT 주간 작업 발표 자료

기준: 2026년 10월 29일까지 이 작업 폴더와 대화에서 확인한 작업. 팀 전체의 다른 저장소 작업까지 확인한 보고서는 아니다.

## 1. 내가 만든 것은 무엇인가?

**“축소 주차장 영상에서 자동차의 위치를 사각형으로 찾는 경량 객체 탐지 모델 PARKIT Tiny와, 이를 학습·평가하고 카메라 영상에서 비교할 수 있는 실험 도구를 구현했습니다.”**

현재 모델은 이미지 한 장을 받아 차량의 위치 `(x1, y1, x2, y2)`와 신뢰도를 출력한다. 자동차 종류를 세분화하지 않고 `car` 한 종류를 찾는다.

대규모 언어 모델(LLM)이나 대규모 멀티모달 모델(LMM)은 아니다. 발표에서는 **“YOLO 계열의 탐지 아이디어를 참고한 CNN 기반 단일 클래스 경량 객체 탐지 모델”**이라고 설명한다. YOLO 라이브러리의 이름만 바꾼 모델도 아니다. 자체 모델의 신경망·좌표 복원·손실·학습 루프는 별도로 구현했다. 다만 합성곱, 자동 미분, 최적화 같은 기반 기능에는 PyTorch를 사용한다. 새로운 탐지 이론을 발명했다고 주장하는 단계는 아니다.

전체 졸업작품에서 현재 작업의 위치:

```text
카메라 영상
  ↓
차량 탐지: 위치와 신뢰도 출력          ← 이번 작업의 핵심
  ↓
영상 좌표를 주차장 도면 좌표로 변환     ← 향후 통합·검증 대상
  ↓
차량과 주차 구역을 비교해 점유 판정      ← 향후 통합·검증 대상
  ↓
서버·앱에 빈자리 및 안내 정보 표시      ← 향후 통합·검증 대상
```

차량에 박스를 그리는 것과 주차면 점유율을 정확히 계산하는 것은 별도 단계다. 이 폴더의 결과만으로 다중 카메라 통합·호모그래피·서버·앱 연결까지 완료했다고 보고하지 않는다.

학습은 100 epoch를 목표로 시작했으나 90 epoch까지 완료한 뒤 체크포인트 저장 오류로 중단됐다. 이후 임시 파일에 저장한 뒤 교체하는 방식으로 저장 코드를 보완했다. **100 epoch 학습 완료라고 발표하면 안 된다.**

## 3. 모델 구조를 설명하는 방법

### 3-1. 전체 흐름

```text
사진: 원본 1920×1080 등
  ↓ data.py
비율 유지 축소 + 회색 여백(letterbox), RGB, 0~1 정규화
  ↓
입력 텐서: [배치, 3, 640, 640]
  ↓ model.py의 backbone
특징 추출: 윤곽·질감·차량 형태를 구분하는 표현 학습
  ↓ neck
해상도가 다른 특징을 결합
  ↓ 두 개의 head
80×80 격자, 40×40 격자에서 차량 점수와 박스 거리 예측
  ↓ decode
격자 중심에서 좌·상·우·하 거리로 사각형 좌표 복원
  ↓ confidence filter + NMS
낮은 점수와 중복 후보 제거
  ↓
원본 이미지 좌표로 복원 → 차량 박스 표시
```

**설명 대본:** “이미지에서 특징을 추출하는 부분을 백본, 서로 다른 크기의 특징을 합치는 부분을 넥, 실제 위치와 점수를 예측하는 부분을 헤드라고 합니다. 입력 영상을 축소해 처리하고, 마지막에 좌표를 원래 영상 크기로 되돌립니다.”

### 3-2. 실제 코드와 대응

| 구성 | 구현 | 쉬운 설명 |
|---|---|---|
| 기본 연산 | `Conv`: Conv2d + BatchNorm + SiLU | 주변 픽셀을 보면서 특징을 만들고 안정적으로 학습 |
| 경량 블록 | `Block`: depthwise 3×3, pointwise 1×1, residual 연결 | 채널별 공간 계산과 채널 혼합을 나누고 기존 특징에 결과를 더함 |
| 백본 | `stem`, `s4`, `s8`, `s16` | 공간 해상도를 줄이며 특징 채널 수를 늘림 |
| 넥 | `lateral`, nearest upsample, concat, `fuse` | 넓은 영역의 특징을 더 촘촘한 특징과 결합 |
| 헤드 | `Head.obj`, `Head.box` | 차량 존재 점수 1개와 박스 거리 4개를 별도 분기로 예측 |
| 좌표 복원 | `decode` | 격자 중심과 양수 거리로 실제 박스 생성 |
| 학습 손실 | `detection_loss` | 존재 여부와 위치 오차를 합쳐 학습 |
| 후처리 | `predict`, `nms` | 점수 필터, 상위 후보 선택, 중복 제거 |

640 입력, width=16 기준:

| 단계 | 공간 크기 | 채널 수 |
|---|---:|---:|
| 입력 | 640×640 | 3 |
| stem | 320×320 | 16 |
| s4 | 160×160 | 32 |
| s8 | 80×80 | 64 |
| s16 | 40×40 | 128 |
| 결합한 s8 특징 | 80×80 | 64 |
| 탐지 출력 1 | 80×80 | 5 |
| 탐지 출력 2 | 40×40 | 5 |

출력 5개는 차량 점수용 logit 1개와 좌·상·우·하 거리용 값 4개다. 클래스 5개라는 뜻이 아니다. 격자 위치는 총 8,000개지만 필터링 후 일부만 남긴다. 현재 구현은 점수 필터 후 상위 1,000개 후보에 NMS를 적용하고 최대 100개를 반환한다.

- 파라미터: **597,562개, 약 60만 개**.
- 합성곱 연산량: **약 3.959 GFLOPs**. BN·활성화·후처리를 포함한 전체 연산량은 아니다.
- 두 출력의 stride: **8, 16**. 입력에서 8/16픽셀 간격인 격자를 의미한다.
- anchor-free: 미리 정한 여러 크기의 앵커 박스 대신 격자 중심에서 네 방향 거리를 예측한다.
- 모든 블록이 depthwise인 것은 아니다. 경량 블록 외 일반 합성곱도 사용한다.

### 3-3. 학습 방식

1. 사진과 정답 박스를 함께 읽는다. 라벨 형식은 `class center_x center_y width height`, 좌표는 원본 크기 기준 0~1로 정규화되어 있다.
2. 사진 크기를 바꿀 때 정답 박스도 동일한 비율·여백으로 변환한다.
3. 좌우 반전, 밝기·색·대비·색조 변화, 확대·축소·이동, mosaic을 학습 데이터에 적용한다. val/test에는 학습용 증강을 적용하지 않는다.
4. 차량 내부의 중심 부근 격자에 정답을 배정한다. 모델 입력 좌표계에서 차량의 긴 변 96픽셀을 기준으로 기본 담당 해상도를 나누고, 작은 박스가 배정되지 않는 경우 보완한다.
5. 존재 여부에는 focal loss, 박스 위치에는 GIoU loss를 사용한다. 현재 합산은 `존재 손실 + 5 × 박스 손실`이다.
6. AdamW로 가중치를 갱신한다. 기본 학습률 0.001, weight decay 0.0005, cosine 학습률 감소, gradient clipping 10을 코드에 설정했다. 이는 코드 설정 설명이며 모든 실행 인자를 완전히 기록한 실험 관리 시스템은 아직 아니다.
7. epoch마다 val AP50을 보고 최고 모델과 마지막 모델을 각각 저장한다.

“학습”은 코드를 계속 변경하는 작업이 아니라, 정답과 예측의 차이를 이용해 가중치 숫자를 갱신하는 작업이다. epoch는 학습 데이터 전체를 한 번 사용하는 단위다. 같은 27장을 90번 사용했다고 사진이 2,430장의 서로 다른 장면이 되는 것은 아니다.

## 4. 각각의 파일은 무엇인가?

경로는 모두 PARKIT 프로젝트 루트 기준이다. 실행 파일을 `runs/train`에 둔 현재 배치는 유지했으며, 일반적인 소스/결과 폴더 분리까지 완료한 것은 아니다.

### 자주 볼 Python 파일

| 파일 | 역할 | 수정하는 경우 |
|---|---|---|
| `parkit_detector/model.py` | 자체 신경망, 박스 디코딩, 손실, NMS | 모델 구조·학습 목표·자체 추론 후처리 변경 |
| `parkit_detector/data.py` | 이미지·라벨 읽기, letterbox, 증강, 배치 구성, 결과 그림 저장 | 입력 처리·학습 데이터 증강 변경 |
| `parkit_detector/run.py` | 학습·평가·벤치마크 명령, 저장·로딩, BGR 프레임용 Detector | 학습 루프·평가·외부 프로그램 연결 변경 |
| `runs/train/live_detect.py` | 카메라/영상 GUI, 모델 선택, 두 화면 비교, 공통 차량 후처리 | 화면·카메라·모델 연결·표시 수정 |
| `runs/train/capture.py` | 상자 없는 원본 사진·영상 촬영 및 저장 | 촬영 해상도·저장·파일 이름 변경 |

**model.py = 설계 / data.py = 재료 준비 / run.py = 학습·검사 진행 / .pt = 학습 결과 / live_detect.py = 실시간 사용 화면.**

### 보조 코드와 노트북

| 파일 | 역할 |
|---|---|
| `parkit_detector/calibrate.py` | val에서 신뢰도 후보별 F1을 비교해 임계값 선택 |
| `parkit_detector/check.py` | 좌표·출력·역전파·평가 계산 등의 기본 검사 |
| `parkit_detector/report.py` | 학습 기록으로 SVG 곡선 생성 |
| `parkit_detector/inspect_checkpoint.py` | 자체 .pt의 메타데이터·구조·텐서 내용을 읽을 수 있는 요약으로 출력 |
| `parkit_detector/__init__.py` | Python 패키지에서 모델 클래스를 제공 |
| `tests/test_vehicle_nms.py` | 중첩·인접 차량·부분 박스·다른 클래스에 대한 후처리 검사 |
| `PARKIT_Colab.ipynb` | Colab에서 업로드·구현 검사·학습·평가·다운로드하는 실행 순서 |

노트북이 있다는 사실은 그 안의 모든 학습을 Colab에서 완료했다는 뜻이 아니다. 촬영 프로그램은 라벨링이나 학습을 자동으로 수행하지 않는다.

### 가중치 파일 — 이름보다 실제 내용이 중요

| 파일 | 실제 의미 | 주의 |
|---|---|---|
| `runs/train/mymodel.pt` | 자체 PARKIT Tiny의 75 epoch 최적 가중치 | 현재 자체 모델 대표 파일 |
| `runs/train/last.pt` | 자체 모델의 90 epoch 마지막 가중치 | 마지막 모델이 항상 가장 좋은 모델은 아님 |
| `runs/train/best.pt` | 현재는 별도의 Ultralytics YOLO26n 기반 차량 모델 | 자체 model.py로 만든 모델이 아님 |
| `runs/train/yolo26n.pt` | 비교용 별도 Ultralytics 체크포인트 | mymodel.pt와 구조가 다름 |
| `runs/overfit/best.pt`, `last.pt` | 사진 2장으로 구현 검사를 한 모델 | 최종 서비스용 가중치 아님 |

`.pt`는 바이너리 파일이라 텍스트 편집기로 열면 깨져 보인다. `model.py`를 수정해도 기존 .pt가 자동으로 바뀌지 않는다. 구조를 바꾸면 재학습과 호환성 확인이 필요하다.

과거 MODEL_REPORT.md의 `runs/train/best.pt`는 **당시 자체 모델의 저장 이름**이다. 현재 동일한 위치의 파일과 혼동하지 말아야 한다. 이번 발표의 자체 모델 수치는 `mymodel.pt`에 해당한다. 새 자체 학습은 `--out runs/parkit_train`처럼 다른 출력 폴더를 사용해 현재 YOLO 가중치를 덮어쓰지 않도록 한다.

## 5. 데이터와 결과를 어떻게 발표할까?

### 데이터 현황

| 분할 | 사진 | 차량 정답 박스 |
|---|---:|---:|
| train | 27 | 432 |
| val | 6 | 110 |
| test | 6 | 118 |
| 추가 촬영 원본 | 86 | 라벨링 전 |

기존 라벨 데이터 총 39장과 추가 촬영 86장을 구분해서 말한다. **125장으로 학습했다고 말하면 안 된다.** 추가 촬영은 원본 확보 단계다. 연속 촬영 사진을 무작위로 나누면 비슷한 장면이 train과 val/test에 동시에 들어갈 수 있으므로, 촬영 세션·차량 배치별로 분리할 계획이다.

### 자체 모델의 초기 val 결과

| 설정 | Precision | Recall | 오탐 | 누락 |
|---|---:|---:|---:|---:|
| confidence 0.25, 기본 NMS | 66.06% | 99.09% | 56 | 1 |
| confidence 0.45, 기본 NMS | 95.88% | 84.55% | 4 | 17 |

- Precision: 차량이라고 표시한 박스 중 실제 정답인 비율. 낮으면 엉뚱한 박스가 많다.
- Recall: 실제 차량 중 찾아낸 비율. 낮으면 놓치는 차량이 많다.
- AP50: 정답과 IoU 0.5 이상을 맞음으로 판단해, 여러 신뢰도 수준의 탐지 순위를 요약한 값. **96.57%**.
- 정답 매칭은 차량 하나당 예측 하나만 인정한다. 같은 차의 추가 박스는 오탐으로 집계될 수 있다.
- 위 수치는 val 6장의 결과이며 최종 test나 실제 카메라의 정확도라고 해석하지 않는다.
- 자체 101점 보간 평가 구현이다. 공식 COCO 전체 평가기와 동일하다고 주장하지 않는다.
- confidence 0.45는 val 후보들에서 F1이 높았던 설정이다. 모든 환경에서 최적이라는 뜻이 아니다.

**발표 문장:** “차량을 많이 찾는 설정에서는 오탐이 많고, 신뢰도를 높이면 오탐은 줄지만 차량을 놓칩니다. 현재는 두 지표의 균형을 개선하는 단계이며 Precision과 Recall을 동시에 95% 이상 달성하지는 못했습니다.”

### 속도

Mac CPU 4스레드, 640 입력, 검증 이미지 한 장 반복, 예열 10회 후 100회 측정에서 평균 **23.64ms**, p95 **27.76ms**였다. 모델 순전파·디코딩·NMS 범위이며 사진 읽기·전처리·화면 표시·카메라 수신은 제외한다. 따라서 “전체 시스템이 42 FPS로 동작한다”라고 주장하지 않는다. GUI의 기본 분석 주기도 초당 2회로 따로 설정되어 있다.

## 6. 빈 곳과 중복 박스 문제

### 빈 곳에 박스가 생기는 경우

빈 곳을 차량으로 판단하는 오탐이다. 데이터 수만의 문제로 확정할 수 없다. 차량 없는 배경, 주차선·글자·반사·그림자 같은 혼동 사례, 라벨 품질, 촬영 각도 차이, 모델·임계값도 원인이 될 수 있다. NMS는 겹친 후보를 줄이는 기능이라 독립적으로 떨어진 빈 배경의 오탐까지 없애지 못한다.

### NMS가 있어도 중복이 남는 이유

IoU는 `겹친 면적 / 두 박스가 차지하는 전체 면적`이다. 100×100 박스 중앙에 20×20 박스가 완전히 들어 있어도 IoU는 0.04다. 기준 0.5/0.6보다 작아서 기존 NMS가 둘 다 남길 수 있다.

이번 추가 기능은 live_detect.py의 `nested_vehicle`, `merge_vehicles`에 구현했다.

- 신뢰도가 낮은 작은 박스만 추가 제거 대상으로 본다.
- 작은 박스의 90% 이상이 겹쳐야 한다.
- 중심 차이가 큰 박스의 폭·높이 각각 25% 이내여야 한다.
- 신뢰도가 높은 작은 부분 박스 때문에 큰 차량 전체 박스가 삭제되는 것은 막는다.
- GUI 체크박스 또는 `--suppress-nested`로 활성화한다. 기본은 꺼짐이다.

mymodel.pt의 같은 val 6장, confidence 0.25에서:

| 항목 | 기존 | 추가 제거 활성화 |
|---|---:|---:|
| 오탐 | 56 | 51 |
| 실제 차량 검출 | 109 | 108 |
| 누락 | 1 | 2 |
| Precision | 66.06% | 67.92% |
| Recall | 99.09% | 98.18% |
| AP50 | 96.57% | 95.73% |

오탐은 감소했지만 누락과 AP50은 나빠졌다. 따라서 **“중복 문제를 완전히 해결했다”가 아니라 “추가 제거 방법을 구현하고 부작용을 정량적으로 확인해 선택 기능으로 남겼다”**고 설명한다. 설정을 val에서 조정했으므로 독립 평가가 아니다. 사용자가 실제 중복을 보았던 YOLO best.pt의 웹캠 결과를 재현·검증한 실험도 아니다.

또한 GUI는 최신 영상 위에 마지막 분석 결과를 표시하므로 움직이는 상황에서는 화면과 좌표가 일시적으로 어긋날 수 있다. 이것은 정지된 빈 곳의 오탐과 구분해서 분석해야 한다.

## 7. 현재 미완료 사항과 다음 작업

1. 새 사진 라벨링과 품질 점검: 자동차 전체를 일관되게 표시하고 누락을 확인한다. 빈 배경·반사·그림자 장면도 확보한다.
2. 촬영 세션별 데이터 분리: 유사 프레임이 평가에 섞이는 것을 막는다. 새 데이터 반영 전후 결과를 비교한다.
3. 자체 모델의 최신 GUI 연결 수정: 현재 어댑터가 가중치/스크립트 옆에서만 model.py를 찾아 실제 패키지 경로와 맞지 않는다. 이 문제를 수정해야 mymodel.pt의 GUI 실행을 확실히 검증할 수 있다.
4. 실제 사용 모델 표시와 실패 처리 점검: 모델 로딩 실패 후 YOLO26n으로 전환하는 현재 동작이 혼동을 만들 수 있다.
5. 자체 모델 재학습과 공정 비교: 같은 데이터·입력·평가기로 YOLO 모델과 비교한다. 사전학습 사용 여부도 구분한다.
6. 후처리 평가: 중복 수뿐 아니라 실제 차량 누락을 함께 확인하고 설정을 결정한다.
7. test 최종 평가: val에서 설정을 확정한 뒤 별도로 실행한다.
8. 주차면 점유 판정 연결: 카메라 보정·좌표 변환·주차 구역 매칭·시간에 따른 안정화·앱 전달을 통합 검증한다.

환경 측면에서는 effdet 설치가 저장 공간 부족으로 실패했다. 이후 torch 2.8.0 import는 확인했다. 이는 전체 환경 무결성 검사는 아니다. effdet는 EfficientDet 비교 모델용이며 자체 모델에 필요하지 않다. 재학습 전 저장 공간 확보가 필요하다.

## 9. 교수님 예상 질문과 답변

### Q1. 정확히 무엇을 직접 만들었나요?

“자체 CNN 탐지 구조, 격자 기반 박스 디코딩, 정답 배정과 손실 함수, 데이터 증강, 학습·평가·후처리 코드를 구현했습니다. 기반 연산과 자동 미분에는 PyTorch를 사용했습니다. 실시간 프로그램에는 여러 외부 모델을 연결하는 비교 기능도 별도로 들어 있습니다.”

### Q2. YOLO 이름만 바꾼 건가요?

“아닙니다. 자체 model.py의 ParkitTiny와 Ultralytics YOLO는 별도 구조입니다. 다만 백본·넥·헤드, 다중 해상도, NMS처럼 널리 쓰이는 탐지 개념을 참고했습니다. 새로운 이론적 구조의 독창성이나 YOLO 대비 우수성을 입증한 단계는 아닙니다.”

### Q3. LMM을 만들었다고 했는데 언어를 처리하나요?

“아닙니다. 용어를 바로잡으면 CNN 기반 객체 탐지 모델입니다. 현재 입력은 이미지이고 출력은 차량 박스와 신뢰도이며 언어 이해 기능은 없습니다.”

### Q4. 왜 기존 YOLO를 그대로 쓰지 않나요?

“경량 탐지 구조와 학습 과정을 직접 구현하고, 축소 주차장 환경에서 필요한 성능과 연산량을 검증하려는 목적입니다. 실제 배포 모델은 비교 실험 후 선택해야 하며, 자체 모델이 무조건 낫다고 가정하지 않습니다.”

### Q5. 경량이라는 근거가 있나요?

“파라미터가 약 60만 개이고, 640 입력에서 합성곱 기준 약 3.959 GFLOPs입니다. 다만 기존 YOLO보다 빠르다는 결론은 같은 환경의 비교 측정 후에 내려야 합니다.”

### Q6. 데이터 27장으로 충분한가요?

“실제 환경 일반화를 주장하기에는 부족합니다. 초기 구현과 학습 가능성을 확인하는 데이터로 사용했고, 추가 촬영 86장을 라벨링해 확장할 예정입니다. 데이터 수뿐 아니라 배경·각도·조명·가림의 다양성도 보완하겠습니다.”

### Q7. 박스가 432개면 데이터가 충분한 것 아닌가요?

“한 사진의 여러 자동차는 같은 배경과 조명 조건을 공유합니다. 객체 수가 많아도 독립적인 장면 다양성이 충분하다는 뜻은 아닙니다.”

### Q8. 증강하면 데이터 부족을 해결할 수 있나요?

“기존 장면의 색·위치·크기를 변화시켜 학습을 돕지만, 전혀 새로운 배경과 가림을 모두 대신하지는 못합니다. 실제 추가 촬영이 필요합니다.”

### Q9. 학습 데이터 누출은 어떻게 방지하나요?

“유사한 연속 프레임을 무작위로 섞기보다 촬영 세션과 차량 배치 단위로 분리합니다. val은 설정 선택에, test는 마지막 평가에 사용합니다. 현재 작은 분할만으로 새로운 환경 일반화가 확인됐다고 주장하지 않습니다.”

### Q10. 96.57%인데 왜 카메라에서는 잘 안 되나요?

“96.57%는 작은 val 묶음의 AP50이며 카메라 정확도가 아닙니다. 카메라의 각도·조명·배경이 다를 수 있고, AP와 특정 임계값의 Precision도 다른 지표입니다. 실제 사용한 가중치가 YOLO best.pt인지 자체 mymodel.pt인지도 구분해야 합니다.”

### Q11. Precision과 Recall 중 무엇이 더 중요한가요?

“최종 주차 서비스에서 잘못 빈자리로 안내하는 비용과 실제 빈자리를 놓치는 비용을 정의한 뒤 결정해야 합니다. 차량 탐지의 지표만으로 주차면 점유 정확도를 대신하지 않고, 점유 판정 단계에서도 오점유·미검출을 평가하겠습니다.”

### Q12. 모델이 내놓는 신뢰도 0.8은 80% 확률인가요?

“현재는 모델의 차량 점수이며 실제 정답 확률과 일치하도록 보정했다는 검증은 없습니다. 임계값 선택에는 사용할 수 있지만 확률 보장으로 설명하지 않습니다.”

### Q13. 왜 두 해상도에서 예측하나요?

“촘촘한 격자는 작은 차량의 위치를 표현하고, 더 낮은 해상도 특징은 넓은 문맥을 담는 데 사용합니다. 현재 stride 8과 16을 결합합니다. 이 구성이 최선인지는 단일 해상도 등과의 추가 비교가 필요합니다.”

### Q14. focal loss와 GIoU를 왜 쓰나요?

“차량이 없는 격자가 훨씬 많아 쉬운 배경 예제가 학습을 지배하지 않도록 focal loss를 사용했습니다. 박스는 좌표 차이뿐 아니라 공간 겹침과 배치를 반영하도록 GIoU loss를 사용했습니다. 현재 데이터에서 다른 손실보다 우수하다는 비교 실험은 아직 없습니다.”

### Q15. 작은 데이터에 과적합한 것 아닌가요?

“가능성이 있습니다. 2장으로 100%를 달성한 결과는 구현이 학습 가능한지 확인하는 검사일 뿐 성능 증거가 아닙니다. 별도 장면의 검증·최종 test와 추가 데이터로 일반화를 확인해야 합니다.”

### Q16. NMS가 있는데 중복 박스가 왜 남나요?

“기존 NMS는 IoU로 판단합니다. 작은 박스가 큰 박스 안에 들어가면 포함되어 있어도 IoU가 낮아 둘 다 남을 수 있습니다. 박스 포함 비율과 중심 거리로 보완하는 옵션을 구현했습니다.”

### Q17. 그러면 중복 문제는 해결됐나요?

“완전 해결은 아닙니다. 일부 오탐을 줄였지만 실제 차량 누락이 늘어 기본 적용하지 않았습니다. 모델·데이터 개선과 함께 검증해야 합니다. 특히 문제가 관찰된 YOLO best.pt의 실제 영상 검증은 남아 있습니다.”

### Q18. confidence를 높이면 끝 아닌가요?

“오탐은 줄지만 낮은 점수의 실제 차량도 제거됩니다. 실제 val에서도 0.25에서 0.45로 높이면 오탐은 56→4로 줄었지만 누락은 1→17로 늘었습니다.”

### Q19. 왜 최종 epoch 대신 75 epoch를 쓰나요?

“마지막 학습 시점이 검증 성능 최고 시점과 같지는 않습니다. val AP50이 가장 높았던 75 epoch를 대표 가중치로 선택하고, 90 epoch는 마지막 상태로 별도 보관했습니다.”

### Q20. 실시간 처리가 가능한가요?

“초기 CPU 측정에서 모델·디코딩·NMS 평균은 23.64ms였습니다. 하지만 전처리·카메라·GUI를 포함하지 않았으므로 전체 지연은 추가 측정해야 합니다. 현재 GUI는 CPU 사용을 조절하기 위해 기본 분석 주기가 초당 2회입니다.”

### Q21. Windows에서 개발해도 Mac에서 되나요?

“경로 처리·카메라 백엔드·폰트·Tk 호환성을 고려한 공용 코드를 사용합니다. 가상환경은 각 OS에서 별도로 만들며 Windows 통과만으로 Mac 동작을 보장하지 않습니다. 최종 Mac에서 검증해야 합니다.”

### Q22. mymodel.pt를 지금 바로 시연할 수 있나요?

“학습 가중치와 별도 평가 경로는 있지만 최신 GUI에서 자체 모델 소스를 찾는 경로 문제가 남아 있습니다. 발표 전에 연결 수정과 실제 카메라 검증을 마쳐야 하며, 아직 완료되지 않았다면 저장된 검증 결과와 한계를 명확히 구분해 설명하겠습니다.”

### Q23. 차량 박스로 어떻게 주차 여부를 판단하나요?

“박스에서 위치 기준점을 정하고 카메라 보정을 거쳐 주차 구역과 비교해야 합니다. 기준점을 단순 박스 하단 중앙으로 잡아도 정확한 접지점이 보장되지는 않아 검증이 필요합니다. 여러 프레임에서 상태를 안정화하는 방법도 필요합니다. 현재 탐지 모델만으로 이 단계까지 완료되지는 않았습니다.”

### Q24. 실험 재현성은 어떻게 관리하나요?

“코드에 시드 42와 학습 기록·가중치 메타데이터를 저장하고 환경 문서를 남겼습니다. 다만 모든 실행 인자·데이터 버전·코드 버전의 자동 추적까지 구축하지는 못했습니다. 향후 실험별 폴더와 설정 기록을 강화하겠습니다.”

### Q25. AI 도구를 이용했다면 본인이 한 일은 무엇인가요?

“AI 코딩 도구의 도움을 받아 구현·분석·정리했고, 프로젝트 요구 정의, 촬영, 실행 확인, 문제 제보와 개선 방향 결정에 참여했습니다. 코드의 입력·출력과 구조, 평가 조건 및 한계를 설명하고 직접 재현할 수 있도록 검토하고 있습니다.”

실제 팀의 역할 분담에 맞게 답변을 조정한다. 본인이 직접 작성·실행하지 않은 내용을 직접 했다고 말하거나, 아직 이해하지 못한 부분을 이해했다고 포장하지 않는다.
